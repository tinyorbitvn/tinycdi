# TinyCDI v1.2.0 — release notes

v1.2.0 is the portal and admin-UI release on the 1.x line. The portal
moves to the Orbit design system's icon set (Tabler 3.48 outline) and
gets a design-system visual refresh — duotone sidebar glyphs, admin
tabs, a mobile drawer, a skip link and sortable table headers — and
the admin area gains the pages the API already let a tenant admin
drive: tenant-wide workspace **Start**/**Restart** actions, a
retained-data page, a users page, and paginated, sortable tables
throughout. On top of the UI work, three platform changes land: the
per-template `clipboardPolicy` is now enforced by the KasmVNC session
server itself — copy/paste inside a session had never worked, the
server pinned both directions off for every template; a tenant admin
can now **cap** session data transfer with a session-policy ceiling
(ADR 0010 — the clipboard channel in v1.2, file transfer in v1.3);
and the tenant-admin role is no longer hard-wired to the literal
`tenant-admin` IdP group — the accepting group set is configurable.
Merged since v1.1.0: #172–#187.

The release carries **one database migration** — 024, the
`tenant_session_policy` table plus `launch_ticket.session_policy`,
forward-only and additive — and **one additive CRD field**, the
optional `spec.sessionPolicy` on the `Workspace` CRD (still
`v1alpha1`, outside the 1.0 stable-surface contract by design). The
`/v1` HTTP API is **additive only**: two new admin routes
(`GET`/`PUT /v1/admin/tenants/{tenant}/session-policy`) and new
optional fields and enums — no existing operation, field or enum
value changes meaning (`docs/versioning.md`).

## Upgrading from 1.1.x

The procedure is `docs/runbooks/upgrade.md`. Unlike the 1.0→1.1
upgrade this release changes the CRDs and runs a migration; the
order that minimizes user-visible impact is still **CRDs → release**:

- **Apply the chart CRDs.** `deploy/helm/tinycdi/crds/` gains the
  optional `spec.sessionPolicy` property on `workspaces`, and both
  CRDs pick up a description-only change on `clipboardPolicy` — no
  schema, enum or required change. Helm never upgrades `crds/`:
  apply them first (`kubectl diff -f deploy/helm/tinycdi/crds/`,
  review, then `kubectl apply -f deploy/helm/tinycdi/crds/`) or let
  the GitOps/ArgoCD sync carry them, per the runbook's Argo CD note.
  The order is safe either way — verified on rc.2: against the
  **old** CRD the API server simply prunes the stamped field and the
  runtime pod env falls back to the recorded template snapshot (the
  designed pre-field fallback), so the release runs correctly before
  the CRD lands and picks the ceiling up the moment it does.
- **Migration 024 runs on backend start** — additive and
  forward-only; a rolling upgrade needs the standard pre-push e2e
  gate per the repo's migration rule. It creates
  `tenant_session_policy` and adds `launch_ticket.session_policy`
  (the resolved policy vector recorded at mint). A tenant with no
  session-policy row behaves exactly as 1.1.x — `FollowTemplate`
  everywhere.

**New chart values — additive, safe defaults:**

| Value | Default | Effect |
|---|---|---|
| `oidc.tenantAdminGroups` | `["tenant-admin"]` | the verified `groups`-claim values that grant the tenant-admin role — rendered unconditionally as `--tenant-admin-groups` on the backend. Exact match, the same semantics as `oidc.requiredGroups` (a Keycloak full path `"/x"` does **not** match `"x"`). An explicitly **empty** list is a schema/startup error — there is no "nobody is admin" mode. `backend.extraArgs`/`extraEnv` may not carry `--tenant-admin-groups`/`TCDI_TENANT_ADMIN_GROUPS` (denied unless `dev.enabled`). The default is byte-for-byte equivalent to 1.1.x behaviour. **Misconfiguration is a privilege grant** — see Security below |

**Behaviour changes operators must check:**

- **Clipboard now actually transfers where a template allows it.**
  Templates on `Send`/`Receive`/`Bidirectional` silently moved no
  clipboard data before: both runtime paths pinned KasmVNC's
  server-side DLP flags off for every template. They now transfer
  clipboard in the directions the template declares — enforcement
  lands on each workspace's **next start** (pod specs are immutable;
  running sessions are never restarted or disrupted). Templates on
  `Disabled` see no change. Details under "Clipboard policy now
  enforced by the session server" below.
- **The announced `ClusterOnly` default flip did not ship.** The
  v1.1.0 notes announced that unrestricted `ClusterOnly` egress
  becomes restricted by default in v1.2 — the flip is **not** in
  this release: the default stays unrestricted (deprecated), and
  the chart's install NOTES, README, and values comments now name
  the deferral (planned for v1.3). Confine egress
  with `runtime.networkProfiles.clusterOnly.egress*` as v1.1
  recommended — deployments that set the narrowing see no behaviour
  change whenever the flip lands. See `docs/releases/v1.1.0.md`
  ("Upgrading") and the chart README "ClusterOnly egress".

## Portal and admin UI

- **Orbit icon set** (#172). The hand-drawn icon geometry is
  replaced by the official Tabler 3.48 outline artwork — inline SVG
  only, no new runtime dependency, exports renamed to the Orbit
  manifest names and the set extended for the v1.2 admin work.
- **Design-system visual refresh** (#174, #182). The sidebar
  navigates with Orbit Dashboard duotone glyphs (retained data uses
  the attachment concept); the admin sub-nav moves to the design
  system's `Tabs` with roving tabindex and arrow-key activation;
  below 48rem the sidebar collapses behind a hamburger into a
  focus-trapped drawer; a "Skip to content" link is the first shell
  element; sortable headers expose `aria-sort`; filter inputs gain a
  search ornament and a localized clear button. Verified in light +
  dark themes and vi.
- **Admin workspace actions** (#173). The tenant workspaces table
  and the shared detail page gain **Start** on Stopped/Failed rows
  and **Restart** — client-side sequencing (stop → poll until
  Stopped → start) with live progress in the confirm dialog, which
  states it is two operations, names the owner ("acting on {owner}'s
  workspace") and notes the action consumes the owner's
  running-workspace limit and the tenant quota. Rows with more than
  two actions fold into a menu. **Connect stays owner-only** — no
  admin takeover in v1.2; non-owner viewers see an "acting as tenant
  administrator" banner instead. No backend or contract change —
  the `/v1` routes already accepted the tenant-admin role.
- **Admin retained-data page** (`/admin/data`, #173). A tenant-scope
  disk table — ID, owner, state, size, source workspace, attach
  target, age — with purge via the existing nonce + typed-confirm
  dialog and per-row polling while the sweep runs. The admin
  Overview gains a retained-data stat card.
- **Users page** (`/admin/users`, #176). A tenant admin can now see
  every principal known to the tenant — the union of the admin quota
  view's `users[]` usage rows and the per-user limit rows — with
  running workspaces, the CPU/memory/storage usage vector, the
  running limit and its effective value, and the retained-disk
  count. A per-user detail page (`/admin/users/{subject}`) lists
  that user's workspaces and retained disks and reuses the per-user
  limit editor. No `/v1` API change; all reads are the existing
  tenant-admin endpoints.
- **Paginated, sortable tables** (#177). The admin lists —
  workspaces, retained data, templates, users — and the personal
  retained-data list now page client-side (default 50 rows,
  selectable 25/50/100) and sort by column, stably and with
  `aria-sort` on the header.

## Clipboard policy now enforced by the session server

The per-template `spec.clipboardPolicy` is now enforced by the KasmVNC
session server, not only by client-side parameters. Before this change
the policy was recorded on the template, mapped into the client's
`clipboard_up`/`clipboard_down` flags and the session iframe's `allow`
attribute, and bound into the launch ticket — but the runtime image's
KasmVNC `data_loss_prevention.clipboard` block pinned both directions
off for every template, so the server dropped all clipboard traffic no
matter what the template declared (copy/paste inside a session simply
did not work).

The operator now renders the template's policy into the runtime pod as
`TCDI_CLIPBOARD_POLICY`, and the session entrypoints (the linux-base
image entrypoint and the injected kasm-adapter one) render the
`data_loss_prevention.clipboard` block from it into
`$HOME/.vnc/kasmvnc.yaml`, which merges after the system policy.
Direction semantics — defined once, from the user's point of view, in
`internal/api/openapi.yaml`:

| Policy | Effect |
|---|---|
| `Disabled` | clipboard blocked in both directions (unchanged) |
| `Send` | client → workspace only |
| `Receive` | workspace → client only (primary selection included) |
| `Bidirectional` | both directions |

Unset or unknown values render `Disabled` — the wiring fails closed.
Client-side overrides and DLP logging stay off.

**Behaviour change for `Send`/`Receive`/`Bidirectional` templates:**
clipboard redirection now actually works in the directions the
template allows, where it was silently inert before. Templates on
`Disabled` see no change.

**Running workspaces are not restarted.** Pod specs are immutable;
the new env var only lands on pods built after the upgrade — i.e.
each workspace picks the enforcement up at its next start, and an
in-flight session is never disrupted. Policy changes on a template
family remain governed by the existing compatibility guard
(`clipboard-policy-changed` skip reason). No CRD or API shape change;
no migration.

## Tenant session policy ceiling (ADR 0010)

A tenant admin can now cap what data may move between a user's device
and their workspace — the first channel is the clipboard — from the
new **Session policy** admin page (`/admin/session-policy`) or
directly via the additive API:

- `GET /v1/admin/tenants/{tenant}/session-policy`
- `PUT /v1/admin/tenants/{tenant}/session-policy` (tenant-admin only,
  CSRF + `If-Match` optimistic concurrency, `412 PRECONDITION_FAILED`
  on a stale version, audited)

The ceiling can only **narrow** a template's own `clipboardPolicy`,
never widen it — the effective policy is the meet of the template's
and the ceiling (`Send ∩ Receive = Disabled`; a `Disabled` ceiling
turns everything off). `FollowTemplate` is the default on every
channel and means "not narrowed"; a tenant with no session-policy row
behaves exactly as before, and setting every channel back to
`FollowTemplate` deletes the row — the upgrade changes nothing until
an admin acts.

**Launch tickets gain a `sessionPolicy` field** (additive) carrying
the resolved vector the ticket recorded; the portal renders the
session frame's clipboard permissions from it. On the operator side
the `Workspace` CRD gains an optional `spec.sessionPolicy` field the
control plane stamps at create/start; the runtime pod env
`TCDI_CLIPBOARD_POLICY` prefers it and falls back to the recorded
template snapshot on pre-field CRs. `fileTransfer` appears in the
schema as the inert v1.3 channel — only its defaults are accepted.

Tightening takes effect on two clocks: the next minted connection
ticket carries the new client flags **immediately**, while a running
workspace's server-side clipboard enforcement picks the ceiling up
at its **next start** (pod specs are immutable — no mid-session
restart). The admin page previews the effective policy per template;
the operator runbook is `docs/runbooks/session-policy.md`.

**Migration note:** this release carries DB migration 024
(`tenant_session_policy` + `launch_ticket.session_policy`),
forward-only and additive; a rolling upgrade needs the standard
pre-push e2e gate.

## Configurable tenant-admin groups

The tenant-admin role was hard-wired to the literal `groups`-claim
value `tenant-admin`: deployments whose IdP already carries an admin
group under another name (e.g. the `platform-admins` group gating
login via `oidc.requiredGroups`) could not grant the role without
renaming groups at the IdP.

- New backend flag `--tenant-admin-groups=<csv>` (env
  `TCDI_TENANT_ADMIN_GROUPS`, repeatable or CSV) names the verified
  `groups`-claim values that grant tenant administration —
  tenant-wide list/get, `scope=tenant`, retained-disk attach/purge
  and the `/v1/admin/*` quota, user-limit and session-policy
  endpoints. The match is exact, the same semantics as
  `--required-groups` (a Keycloak full path `"/x"` does **not** match
  `"x"`). The default is exactly `tenant-admin`, so an upgrade
  changes nothing until the flag is set; an explicitly empty list is
  a startup error — there is no "nobody is admin" mode.
- New chart value `oidc.tenantAdminGroups` (list, default
  `["tenant-admin"]`) renders `--tenant-admin-groups` on the
  backend; `backend.extraArgs`/`extraEnv` may not set the flag/env
  equivalent (`--tenant-admin-groups` / `TCDI_TENANT_ADMIN_GROUPS`
  join the denied sets unless `dev.enabled`).
- The `/v1/me` role name stays `tenant-admin` regardless of the
  configured groups — no API change. Membership resolves once per
  request inside `RequireAuth`; principals attached any other way
  fail closed.
- SECURITY: every member of a listed group holds tenant-wide read,
  workspace stop/start, retained-disk attach/purge and
  quota/per-user-limit admin — misconfiguration is a privilege
  grant. Review the IdP group membership when changing the value
  (see SECURITY.md, operator checklist).

## Security

Each item below names its threat-model row in
`docs/security/threat-model.md`.

### Template `clipboardPolicy` never reached the session server — S40, fixed in v1.2 (#178)

The clipboard policy was declared per template and mapped into every
client-side layer — the gateway's `clipboard_up`/`clipboard_down`
redirect flags, the session iframe's `allow` attribute, the launch
ticket — but both runtime paths pinned KasmVNC's
`data_loss_prevention.clipboard.*.enabled=false`, so the server
dropped all cut-text traffic regardless of the template
(`-SendCutText 0 -AcceptCutText 0 -SendPrimary 0`; proven end to end:
real-browser copy/paste failed on the released image and succeeded
with only the DLP flags flipped). Client flags are hints, not
enforcement — the server is. `buildPod` now carries the spec value
verbatim as `TCDI_CLIPBOARD_POLICY` and both session entrypoints
render the DLP block from it — unset/unknown fails closed to
`Disabled`, `primary_clipboard_enabled` follows `server_to_client`,
client overrides and DLP logging stay off. Enforcement lands at each
workspace's next start and never disrupts a running session; policy
drift across a family re-point stays guarded by the E2 skip reason
`clipboard-policy-changed`.

### Tenant session-policy ceiling — new in v1.2 (ADR 0010, #181)

The ceiling is a **narrow-only** control: the effective policy is the
meet of the template's `clipboardPolicy` and the tenant ceiling, so
no admin action can widen past what the GitOps-published template
allows — there is no per-template override and no "force enable" in
v1. `FollowTemplate` is represented by *no row* (or an
all-defaults PUT deleting it), which is what keeps the change
additive: a tenant that never sets a ceiling resolves exactly the
template policy. Writes ride the same discipline as tenant quota —
tenant-admin only, CSRF, `If-Match` optimistic concurrency on an
opaque change token, a single conditional statement that cannot be
raced, and every write audited (`admin.session_policy.{set,clear}`).
The documented residual is the propagation clock: a tightened
ceiling reaches new connection tickets immediately but a running
workspace's server-side DLP only at its next start — the window is
bounded by the template's own policy, never wider than what was
allowed before the ceiling existed (ADR 0010 §3).

### Tenant-admin role hard-wired to a literal IdP group name — S41, fixed in v1.2 (#183)

Every admin gate used to consult `InGroup("tenant-admin")` directly,
so a deployment whose IdP already names its admin group differently
could not grant the role without IdP renames.
`--tenant-admin-groups` / `oidc.tenantAdminGroups` now names the
verified `groups`-claim values that grant it — exact match, default
exactly `tenant-admin`, an explicitly empty list a startup error.
Membership resolves once per request into a single principal flag
every gate shares (a source-level test fails on a reintroduced raw
literal check); principals attached outside `RequireAuth` fail
closed. **Misconfiguration is a privilege grant**: every member of a
listed group gets tenant-wide read, workspace stop/start,
retained-disk attach/purge and quota/per-user-limit admin — review
the IdP group membership when changing the value. The chart pins the
posture (schema `minItems: 1`, flag/env equivalents denied in
`extraArgs`/`extraEnv`, install NOTES echoes the configured groups).

## Release-candidate verification

v1.2.0 was verified on two release candidates — rc.1, cut after the
clipboard fix (#172–#178), and rc.2, the full release tree
(#172–#186) — end to end on a throwaway install and as real rollouts
on the maintainer's development deployment.

**End-to-end on a throwaway install (rc.2).** A disposable install
on v1.1.0 — all eight published images cosign-verified — was
upgraded in place to the signed rc.2 chart and images with
`helm upgrade --skip-crds` plus the reviewed CRD apply, then
exercised gate by gate (all PASS):

- **Upgrade (U1):** a live desktop stream held open through the
  rollout dropped once (~1.1 s) and reconnected in-frame to a new
  stream epoch — no relaunch, no re-login, zero 5xx in the rollout
  window, zero pod restarts. `schema_migrations` moved 23 → 24
  exactly once — idempotent across a second backend start — and the
  024 objects (`tenant_session_policy`,
  `launch_ticket.session_policy`) were present with all pre-existing
  rows intact.
- **Session policy (P1):** a tenant with no row reads
  `FollowTemplate`; `PUT clipboard=Disabled` with `If-Match: *`
  creates the row and returns its change token; `If-Match: *` on a
  live row answers `412`, an unparseable token answers `412`, a
  non-admin PUT answers `403`, a missing CSRF header answers `403`,
  a missing `If-Match` answers `400`. A connection minted on a
  `Bidirectional` template under the `Disabled` ceiling recorded the
  resolved `Disabled` on the ticket — the launch redirect carried
  `clipboard_up=false&clipboard_down=false` — and a `FollowTemplate`
  PUT deleted the row. Every read and write, denials included, is
  audited (`admin.session_policy.{get,set,clear}`).
- **Pre-field CRD fallback (P1+):** on the pre-field `workspaces`
  CRD the stamped `spec.sessionPolicy` is pruned and the pod env
  falls back to the recorded template snapshot — a `Bidirectional`
  workspace under a `Disabled` ceiling kept `Bidirectional`
  server-side, the designed behaviour until the CRD lands. On the
  field-present CRD the same class stamped `Disabled` into
  `spec.sessionPolicy` and the pod env followed it.
- **Admin groups (A1):** with `oidc.tenantAdminGroups` set to a
  custom group, a member resolves `roles=[user,tenant-admin]` and
  the admin routes answer 200; a member of only the literal
  `tenant-admin` group resolves `roles=[user]` and is refused `403`.
  The default render emits `--tenant-admin-groups=tenant-admin`; an
  empty list fails values-schema validation.
- **Clipboard (C1):** a real-browser round-trip on the rc.2 runtime
  images — a `Disabled` workspace blocks copy and paste in both
  directions; a `Bidirectional` workspace round-trips text in both.
- **Admin UI (UI1):** all seven admin sections render under a
  custom-group admin — Overview, Workspaces, Quota, Session policy,
  Templates, Data, Users — the retained-data sidebar icon is the
  attachment glyph, and a 30-row retained-data table paginates
  ("Showing 1–25 of 30").
- **Smoke (S1):** `hack/e2e/smoke.sh --sign-out-everywhere` passed
  all 21 checks against the upgraded install — the v1.1.0 baseline
  had passed 20 with one documented quota SKIP.

Teardown removed the install completely — every e2e namespace gone,
no persistent volumes left, the shared cluster identical to its
pre-install state.

## Known limitations

The standing limitations of v1.1.0 still apply — see
`docs/releases/v1.1.0.md` ("Known limitations") for the full list.
Carry-forwards and new residuals for this release:

- **File transfer ships in v1.3, not v1.2** (ADR 0010). The
  `fileTransfer` channel exists in the session-policy schema but is
  inert — only its defaults are accepted. Turning it on takes a
  published `spec.fileTransferPolicy` on a template (default
  `Disabled`, today's posture) *and* a tenant ceiling; both arrive
  with T11 in v1.3. The session-policy page shows the control
  disabled.
- **Session-policy tightening reaches running workspaces at their
  next start.** A tightened ceiling reaches new connection tickets
  immediately, but a running workspace's server-side clipboard
  enforcement only picks it up when the pod is next built — pod
  specs are immutable, and v1 adds no "restart affected workspaces"
  action. Between the PUT and the next start the server permits the
  old policy (the client flags restrain an unmodified client only);
  the residual is bounded by the template's own policy. An admin who
  cannot wait stops the workspace or revokes its leases (ADR 0010
  §3).
- **The admin Users page is not a tenant directory.** `/admin/users`
  lists only principals who have used the tenant — a quota usage row
  or a per-user limit row. A user who has never held a workspace,
  retained disk or limit override does not appear. Listing every
  tenant member needs a future additive API (e.g.
  `GET /v1/admin/tenants/{tenant}/users` backed by the principal
  directory).
- **Client-side table paging.** Tables still read the whole list
  client-side (up to 4000 records, with the existing truncated
  notice beyond that); server-side paging/sort params remain a
  future additive `/v1` extension.
- **Deleting a workspace's runtime pod leaves it `Failed`.** Pod
  deletion is terminal, not self-healed: the `runtimeGeneration`
  fencing that protects a session's pod means a pod removed out from
  under a workspace is never rebuilt, and `desiredState` changes do
  not resurrect it (tracked for a future release).
- **A first cold connect can stall.** A first connection against a
  just-Ready workspace can stall before the session iframe redeems
  the launch ticket — observed once during e2e verification; on
  retry, with the pod warm, the full mint→connect flow took
  seconds. Tracked.
- **`ClusterOnly` stays unrestricted until the deferred flip
  ships.** See Upgrading — a `ClusterOnly` workspace may still reach
  any pod in any namespace on any port; confinement rests on
  destination-side ingress policies unless
  `runtime.networkProfiles.clusterOnly.egress*` is set.
- Carried forward from v1.1.0: the KasmVNC `EMFILE` residual under
  sustained direct saturation above the gateway cap; the
  digest-cleanup TOCTOU window and uncovered legs; client-side
  serial checks not wired on the internal mTLS clients;
  `workspace_revocation` rows are not pruned; the audit stream is
  stdout JSONL (delivery, retention and tamper evidence are the
  operator's log pipeline); per-prefix rate budgets still multiply
  across the prefixes a client holds; DNS egress is allowed on every
  network profile including `Isolated` by design; the
  single-maintainer residual stays accepted, mitigated by the
  required `release`/`runtime-train` environment approvals; no
  independent audit yet — one is planned on the 1.x line; and the
  non-concurrent `CREATE INDEX` builds of migrations 020/023 remain
  a quiet-window item per `docs/runbooks/upgrade.md`.
