# TinyCDI v1.2.0 — release notes (draft)

## Admin portal

- **Users page** (`/admin/users`): a tenant admin can now see every
  principal known to the tenant — the union of the admin quota view's
  `users[]` usage rows and the per-user limit rows — with running
  workspaces, the CPU/memory/storage usage vector, the running limit and
  its effective value, and the retained-disk count. A per-user detail page
  (`/admin/users/{subject}`) lists that user's workspaces and retained
  disks and reuses the per-user limit editor. No `/v1` API change; all
  reads are the existing tenant-admin endpoints.
- **Paginated, sortable tables.** The admin lists — workspaces, retained
  data, templates, users — and the personal retained-data list now page
  client-side (default 50 rows, selectable 25/50/100) and sort by column.

## Clipboard policy now enforced by the session server

The per-template `spec.clipboardPolicy` is now enforced by the KasmVNC
session server, not only by client-side parameters. Before this change
the policy was recorded on the template, mapped into the client's
`clipboard_up`/`clipboard_down` flags and the session iframe's `allow`
attribute, and bound into the launch ticket — but the runtime image's
KasmVNC `data_loss_prevention.clipboard` block pinned both directions off
for every template, so the server dropped all clipboard traffic no matter
what the template declared (copy/paste inside a session simply did not
work).

The operator now renders the template's policy into the runtime pod as
`TCDI_CLIPBOARD_POLICY`, and the session entrypoints (the linux-base
image entrypoint and the injected kasm-adapter one) render the
`data_loss_prevention.clipboard` block from it into
`$HOME/.vnc/kasmvnc.yaml`, which merges after the system policy. Direction
semantics — defined once, from the user's point of view, in
`internal/api/openapi.yaml`:

| Policy | Effect |
|---|---|
| `Disabled` | clipboard blocked in both directions (unchanged) |
| `Send` | client → workspace only |
| `Receive` | workspace → client only (primary selection included) |
| `Bidirectional` | both directions |

Unset or unknown values render `Disabled` — the wiring fails closed.
Client-side overrides and DLP logging stay off.

**Behaviour change for `Send`/`Receive`/`Bidirectional` templates:**
clipboard redirection now actually works in the directions the template
allows, where it was silently inert before. Templates on `Disabled`
see no change.

**Running workspaces are not restarted.** Pod specs are immutable; the
new env var only lands on pods built after the upgrade — i.e. each
workspace picks the enforcement up at its next start, and an in-flight
session is never disrupted. Policy changes on a template family remain
governed by the existing compatibility guard (`clipboard-policy-changed`
skip reason). No CRD or API shape change; no migration.

## Tenant session policy ceiling (ADR 0010)

A tenant admin can now cap what data may move between a user's device
and their workspace — the first channel is the clipboard — from the new
**Session policy** admin page (`/admin/session-policy`) or directly via
the additive API:

- `GET /v1/admin/tenants/{tenant}/session-policy`
- `PUT /v1/admin/tenants/{tenant}/session-policy` (tenant-admin only,
  CSRF + `If-Match` optimistic concurrency, `412 PRECONDITION_FAILED` on
  a stale version, audited)

The ceiling can only **narrow** a template's own `clipboardPolicy`,
never widen it — the effective policy is the meet of the template's and
the ceiling (`Send ∩ Receive = Disabled`; a `Disabled` ceiling turns
everything off). `FollowTemplate` is the default on every channel and
means "not narrowed"; a tenant with no session-policy row behaves
exactly as before, and setting every channel back to `FollowTemplate`
deletes the row — the upgrade changes nothing until an admin acts.

**Launch tickets gain a `sessionPolicy` field** (additive) carrying the
resolved vector the ticket recorded; the portal renders the session
frame's clipboard permissions from it. On the operator side the
`Workspace` CRD gains an optional `spec.sessionPolicy` field the
control plane stamps at create/start; the runtime pod env
`TCDI_CLIPBOARD_POLICY` prefers it and falls back to the recorded
template snapshot on pre-field CRs. `fileTransfer` appears in the
schema as the inert v1.3 channel — only its defaults are accepted.

Tightening takes effect on two clocks: the next minted connection
ticket carries the new client flags **immediately**, while a running
workspace's server-side clipboard enforcement picks the ceiling up at
its **next start** (pod specs are immutable — no mid-session restart).

**Migration note:** this release carries DB migration 024
(`tenant_session_policy` + `launch_ticket.session_policy`), forward-only
and additive; a rolling upgrade needs the standard pre-push e2e gate.

## Known limitations

- **The admin Users page is not a tenant directory.** `/admin/users` lists
  only principals who have used the tenant — a quota usage row or a
  per-user limit row. A user who has never held a workspace, retained disk
  or limit override does not appear. Listing every tenant member needs a
  future additive API (e.g. `GET /v1/admin/tenants/{tenant}/users` backed
  by the principal directory).
- **Client-side table paging.** Tables still read the whole list
  client-side (up to 4000 records, with the existing truncated notice
  beyond that); server-side paging/sort params remain a future additive
  `/v1` extension.
