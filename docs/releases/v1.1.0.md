# TinyCDI v1.1.0 — release notes (draft)

## Terminal-row retention for `connection_lease` / `launch_ticket` (SR-4-F5)

Both session-layer tables are append-mostly: a ticket row is written per
launch and a lease row per redemption, and nothing ever removed the rows
after they died. On a long-lived deployment that growth made every
sign-out revocation scan and any future index build cost more the older
the install got — the SR-4-F5 residual from the v1.0 review.

The backend leader replica now runs an hourly retention sweep that
deletes rows terminal for longer than the configured window in bounded
batches (500 rows per statement, pausing between batches, one sweeper
via the Postgres leader lock):

- `connection_lease` rows in `revoked` / `expired` / `superseded` state,
  aged by `closed_at` (the terminal timestamp every transition writes).
- `launch_ticket` rows consumed, revoked or past `expires_at`, aged by
  the matching terminal timestamp.

Live leases and outstanding tickets are never touched, and no reader
depends on the deleted history — every sign-out, redeem, cookie-resolve
and post-restore path predicates on live/outstanding rows only.

Configuration is additive with a safe default:

- flag `-terminal-retention-days` (env `TCDI_TERMINAL_RETENTION_DAYS`),
  default `30`; `0` disables the sweep.
- chart value `backend.retention.terminalRowDays: 30` — same semantic.

New metrics: `tinycdi_retention_rows_pruned_total{table}` and
`tinycdi_retention_last_success_timestamp_seconds` (documented in
`docs/runbooks/observability.md`); one INFO log line per pass carries
the counts. See `docs/runbooks/capacity.md` for the bounded-growth note
and `docs/security/review-v1.0.md` §6 for the closed residual.
