# TinyCDI v1.1.0 — release notes (draft)

## Upgrading

- **`ClusterOnly` egress default flips in v1.2.** In v1.1 the default is
  **unchanged** — a `networkProfile: ClusterOnly` workspace may still
  reach any pod in any namespace on any port — but that default is
  deprecated and becomes restricted egress in v1.2. Two ways to prepare:
  - **Opt in now (recommended):** set
    `runtime.networkProfiles.clusterOnly.egressNamespaceSelector`
    (e.g. `matchExpressions: [{key: workspaces.cdi.tinyorbit.vn/tenant,
    operator: Exists}]` to confine egress to the managed namespaces),
    plus optional `egressPodSelector` / `egressPorts`. Deployments that
    set the narrowing see no behaviour change at the v1.2 flip — see the
    chart README "ClusterOnly egress".
  - **Keep today's posture:** when upgrading to v1.2, pin the explicit
    unrestricted value the v1.2 notes will document. Until then the
    chart's install NOTES print a WARNING whenever a seeded `ClusterOnly`
    template runs with the narrowing unset.

## Gateway: per-workspace concurrent upstream-stream cap

The session gateway now bounds the number of live upstream connections a
single workspace may hold through one replica: `-session-stream-cap`
(default **32**, env `TCDI_SESSION_STREAM_CAP`, chart value
`backend.sessionStreamCap`, minimum 1 — the bound cannot be disabled;
choose a large value for runtimes that do not need it). Websocket streams
and plain proxied requests count alike. The bound is **per replica**: N
replicas admit at most N x cap connections to one workspace.

Why: the KasmVNC runtime has no connection cap of its own, and Xvnc's
`select()`/`FD_SET` use on per-connection sockets crashes the process —
with stack corruption — once its fd count crosses `FD_SETSIZE` (1024,
~330 concurrent connections on a clean pod). A reconnect storm used to
surface as upstream `502`s plus a runtime pod restart; it now gets a
deliberate, retryable refusal.

Over the cap the session origin answers `429` + `Retry-After: 1` with the
session-listener error body `{"error": "too_many_streams"}` — same shape
as the existing limiter errors; clients should treat it as retryable (the
KasmVNC client's in-frame reconnect does). The refusal is audited as
`session.stream` denied with error `too_many_streams` and counted on
`tinycdi_rate_limited_total{route="upstream_streams"}`; a new unlabelled
gauge `tinycdi_gateway_upstream_streams` reports the replica's in-flight
upstream count.

Compatibility: additive — new flag/env/chart value with a safe default;
no existing behavior changes for traffic under the cap. The session-origin
error code `too_many_streams` is additive to the session-listener error
surface (the portal `/v1` error enum is unchanged: this refusal is only
ever emitted on the session origin's own `{"error": ...}` shape, like
`rate_limited` before it).

## `<component>.extraEnv` refuses dev-surface and chart-managed env names (SR-3-F2)

`<component>.extraEnv` rendered verbatim — after the chart's managed env
block — so it carried the environment equivalents of the flags the chart
pins closed, plus the env names of security-relevant flags the chart
exposes as first-class values (live whenever the flag is not rendered),
and a duplicate of a chart-managed name silently won. The render now
**fails** — the error names the component, the env var and the value to
set instead — when `dev.enabled` is false and an `extraEnv` entry's name
is either:

| Denied `extraEnv` name | Set instead |
|---|---|
| `TCDI_DEV_INSECURE_DB` / `PGSSLMODE` | `database.tls.mode` (verify-ca/verify-full) |
| `TCDI_DEV_ALLOW_NO_BROKER` | `operator.devAllowNoBroker` (dev-only) |
| `TCDI_METRICS_LISTEN` | `backend.metrics.enabled` |
| `TCDI_KASM_ADAPTER_IMAGE` | `kasmAdapter.enabled` + `kasmAdapter.image.digest` |
| `TCDI_OPERATOR_CN` | `backend.operatorCN` |
| `TCDI_WATCH_NAMESPACES` | `managedNamespaces` |
| `TCDI_REQUIRED_GROUPS` | `oidc.requiredGroups` |
| `TCDI_CONTROL_TOKEN` / `TCDI_GW_CONTROL_TOKEN` / `TCDI_CONTROL_TOKEN_FILE` | `backend.controlToken.existingSecret` |
| `TCDI_TRUSTED_PROXIES` | `backend.trustedProxies` |
| `TCDI_UPSTREAM_CA` | `backend.upstreamCA.existingSecret` |
| `TCDI_OIDC_POST_LOGOUT_REDIRECT` | `oidc.postLogoutRedirect` |
| `TCDI_TENANT_QUOTAS` | `managedNamespaces[].quota` |

- or an env var the chart itself manages for that component (e.g.
  `TCDI_DATABASE_URL`, `TCDI_OIDC_*`, `TCDI_TENANT_*`, `POD_NAMESPACE`,
  `SSL_CERT_FILE`) — a duplicate later in the env list would silently
  win. Non-map or nameless `extraEnv` entries fail the render too.

**Upgrade impact:** an operator carrying one of these names in `extraEnv`
now gets a render error instead of a silently-weakened install — set the
corresponding chart value per the table, or — for development only — set
`dev.enabled: true`, which keeps the escape hatch. Non-listed `extraEnv`
names render unchanged.

## CI / supply chain

- **SR-5-F3 — gate-failed image digests are deleted by the same run.**
  `images.yml`, `release.yml` and `runtime-images.yml` push images by
  digest before the trivy gate; a gate-failed publish run
  used to leave those unsigned manifests pullable-by-digest on GHCR.
  Each workflow now runs a `cleanup` job on failure that deletes
  exactly the versions the run pushed — every pushed index, its
  per-platform and attestation children and its referrers — resolved
  from the run's own `image-ref` artifacts
  (`.github/scripts/cleanup-failed-digests.sh`). Deletion is strictly
  run-scoped — a version goes only when it was created inside the
  run's window and is reachable solely from that run's tree; any
  candidate carrying a non-digest tag or reachable from a tagged
  manifest refuses the whole image (never a sweep, never a deleted
  release). Consumers keep the same guarantee: digests are pinned
  only out of signed manifests and verified with cosign first.
## Terminal-row retention for `connection_lease` / `launch_ticket` (SR-4-F5)

Both session-layer tables are append-mostly: a ticket row is written per
launch and a lease row per redemption, and nothing ever removed the rows
after they died. On a long-lived deployment that growth made every
sign-out revocation scan and any future index build cost more the older
the install got — the SR-4-F5 residual from the v1.0 review.

The backend leader replica now runs an hourly retention sweep that
deletes rows terminal for longer than the configured window in bounded
batches (500 rows per statement, pausing between batches, one sweeper
via the Postgres leader lock):

- `connection_lease` rows in `revoked` / `expired` / `superseded` state,
  aged by `closed_at` (the terminal timestamp every transition writes).
- `launch_ticket` rows consumed, revoked or past `expires_at`, aged by
  the matching terminal timestamp.

Live leases and outstanding tickets are never touched, and no reader
depends on the deleted history — every sign-out, redeem, cookie-resolve
and post-restore path predicates on live/outstanding rows only.

Configuration is additive with a safe default:

- flag `-terminal-retention-days` (env `TCDI_TERMINAL_RETENTION_DAYS`),
  default `30`; `0` disables the sweep.
- chart value `backend.retention.terminalRowDays: 30` — same semantic.

New metrics: `tinycdi_retention_rows_pruned_total{table}` and
`tinycdi_retention_last_success_timestamp_seconds` (documented in
`docs/runbooks/observability.md`); one INFO log line per pass carries
the counts. See `docs/runbooks/capacity.md` for the bounded-growth note
and `docs/security/review-v1.0.md` §6 for the finding this closes.

## `ClusterOnly` egress deprecation notice (SR-2-F8)

`templates/NOTES.txt` now prints a WARNING at install/upgrade when a
seeded template uses `networkProfile: ClusterOnly` while
`runtime.networkProfiles.clusterOnly.egress*` is unset, announcing the
v1.2 restricted-egress default and naming the values to set. The
chart's operator-facing docs also state plainly that `Isolated`
workspaces keep cluster **DNS egress** — a deliberate unidirectional
channel — matching the API/CRD descriptions.
