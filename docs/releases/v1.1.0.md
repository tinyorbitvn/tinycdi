# TinyCDI v1.1.0 — release notes

v1.1.0 is the first minor release on the 1.x line. It closes the
actionable residuals of the v1.0 internal security review — the
`extraEnv` render-guard bypass, per-certificate revocation on the
internal mTLS hop, the `ClusterOnly` egress deprecation notice,
terminal-row retention on the session tables and the
gate-failed-digest cleanup — and adds an availability guard layer
against the KasmVNC runtime's concurrent-connection crash boundary
(a per-workspace upstream-stream cap in the session gateway plus a
file-descriptor clamp in the runtime images). Merged since v1.0.0:
#158–#171.

There is **no database migration and no CRD change** — a 1.0.x
install upgrades with a chart and image bump alone. The `/v1` HTTP
API is unchanged: the one new refusal code, `too_many_streams`, is
emitted only on the session origin's own `{"error": ...}` shape,
which lives outside the `/v1` error enum — the same precedent as
`rate_limited` before it (#147).

## Upgrading from 1.0.x

The procedure is `docs/runbooks/upgrade.md`. This upgrade is the
chart plus the pinned images, nothing else: no `crds/` step (the
`workspaces` and `workspacetemplates` schemas are unchanged from
1.0.x) and no migration.

**New chart values — all additive, safe defaults:**

| Value | Default | Effect |
|---|---|---|
| `backend.retention.terminalRowDays` | `30` | days a terminal `connection_lease`/`launch_ticket` row is kept before the leader replica's hourly sweep deletes it in bounded batches — live leases and outstanding tickets are never touched; `0` disables the sweep |
| `backend.sessionStreamCap` | `32` | per-workspace bound on live upstream connections through ONE replica (websocket streams and plain proxied requests count alike; N replicas admit N × cap). Minimum 1 — the bound cannot be disabled; choose a large value for runtimes that do not need it |
| `backend.tls.internal.revokedSerials.existingSecret` / `.key` | unset / `revoked-serials.txt` | opt-in ADR 0009 per-certificate revocation list for the internal mTLS listener — a mounted Secret of `<serial-hex> <issuer-dn>` lines. Unset = off; the default render is byte-identical |

**Behaviour changes operators must check:**

- **`<component>.extraEnv` can now fail the render** (SR-3-F2, #159).
  `extraEnv` used to render verbatim after the chart's managed env
  block, so it could carry the environment equivalents of the flags
  the chart pins closed, plus the env names of security-relevant
  flags the chart exposes as first-class values, and a duplicate of
  a chart-managed name silently won. When `dev.enabled` is false the
  render now **fails** — the error names the component, the env var
  and the value to set instead — on any of:

  | Denied `extraEnv` name | Set instead |
  |---|---|
  | `TCDI_DEV_INSECURE_DB` / `PGSSLMODE` | `database.tls.mode` (verify-ca/verify-full) |
  | `TCDI_DEV_ALLOW_NO_BROKER` | `operator.devAllowNoBroker` (dev-only) |
  | `TCDI_METRICS_LISTEN` | `backend.metrics.enabled` |
  | `TCDI_KASM_ADAPTER_IMAGE` | `kasmAdapter.enabled` + `kasmAdapter.image.digest` |
  | `TCDI_OPERATOR_CN` | `backend.operatorCN` |
  | `TCDI_WATCH_NAMESPACES` | `managedNamespaces` |
  | `TCDI_REQUIRED_GROUPS` | `oidc.requiredGroups` |
  | `TCDI_CONTROL_TOKEN` / `TCDI_GW_CONTROL_TOKEN` / `TCDI_CONTROL_TOKEN_FILE` | `backend.controlToken.existingSecret` |
  | `TCDI_TRUSTED_PROXIES` | `backend.trustedProxies` |
  | `TCDI_UPSTREAM_CA` | `backend.upstreamCA.existingSecret` |
  | `TCDI_OIDC_POST_LOGOUT_REDIRECT` | `oidc.postLogoutRedirect` |
  | `TCDI_TENANT_QUOTAS` | `managedNamespaces[].quota` |

  or on an env var the chart itself manages for that component (e.g.
  `TCDI_DATABASE_URL`, `TCDI_OIDC_*`, `TCDI_TENANT_*`,
  `POD_NAMESPACE`, `SSL_CERT_FILE`) — a duplicate later in the env
  list would silently win. Non-map or nameless `extraEnv` entries
  fail the render too. An operator carrying one of these names in
  `extraEnv` now gets a render error instead of a silently-weakened
  install — set the corresponding chart value per the table, or —
  for development only — set `dev.enabled: true`, which keeps the
  escape hatch. Non-listed `extraEnv` names render unchanged.

- **`ClusterOnly` install NOTES warning; the default flips in
  v1.2** (SR-2-F8, #161). In v1.1 the default is **unchanged** — a
  `networkProfile: ClusterOnly` workspace may still reach any pod in
  any namespace on any port — but that default is deprecated and
  becomes restricted egress in v1.2. The chart's install/upgrade
  NOTES now print a WARNING whenever a seeded `ClusterOnly`
  template runs with the narrowing unset, naming the values to set.
  Two ways to prepare:
  - **Opt in now (recommended):** set
    `runtime.networkProfiles.clusterOnly.egressNamespaceSelector`
    (e.g. `matchExpressions: [{key: workspaces.cdi.tinyorbit.vn/tenant,
    operator: Exists}]` to confine egress to the managed namespaces),
    plus optional `egressPodSelector` / `egressPorts`. Deployments
    that set the narrowing see no behaviour change at the v1.2 flip
    — see the chart README "ClusterOnly egress".
  - **Keep today's posture:** when upgrading to v1.2, pin the
    explicit unrestricted value the v1.2 notes will document.

- **Runtime images clamp the soft fd limit** (#167). Both runtime
  entrypoints set a soft `RLIMIT_NOFILE` of `min(1000, hard)` before
  launching KasmVNC — no values, flags or API change, runtime image
  behaviour only. Excess connections now fail `EMFILE` and are
  refused instead of corrupting the X server; the hard limit is
  unchanged, so a debug shell can still raise it, and a pod whose
  hard limit is already below the target keeps its ambient bound
  rather than failing to boot (the clamp logs its result and never
  fails startup). See Availability below.

- **The gateway stream cap can refuse connections** (#165). A
  workspace holding more than `backend.sessionStreamCap` live
  upstream connections through one replica gets a deliberate,
  retryable refusal: `429` + `Retry-After: 1` with the
  session-listener error body `{"error": "too_many_streams"}` — same
  shape as the existing limiter errors; clients should treat it as
  retryable (the KasmVNC client's in-frame reconnect does). A
  refusal claims no stream epoch and fences no live connection.

## Release-candidate verification

v1.1.0-rc.1 — the release candidate cut from this tree — was
verified three ways: end to end on a throwaway install, as a real
rollout on the maintainer's development deployment, and on the
supply-chain side.

**End-to-end on a throwaway install.** A disposable install on v1.0.0
— all eight published images cosign-verified — was upgraded in place
to the signed rc.1 chart and images with `helm upgrade --skip-crds`,
the documented upgrade path, then exercised gate by gate (all PASS):

- **Upgrade (U1):** a live desktop stream held open through the
  rollout dropped once (~1 s) and reconnected in-frame to a new
  stream epoch — no relaunch, no re-login, zero 5xx in the rollout
  window and zero pod restarts. `schema_migrations` stayed at 23 and
  the CRD set, schemas and generations were identical before and
  after.
- **Retention (R1):** with `terminalRowDays` lowered to 1, the
  leader's sweep pruned exactly the seeded terminal rows (3 aged
  `connection_lease` + 3 `launch_ticket`) and kept recent,
  outstanding and live rows, logging one INFO line and raising
  `tinycdi_retention_rows_pruned_total{table}` to 3 per table.
- **Stream cap (C1):** with `sessionStreamCap=2` and a websocket
  holding one slot, an 8-request burst was answered 1×`200` + 7×`429`
  — every refusal `Retry-After: 1` + `{"error": "too_many_streams"}`
  — and the freed slot admitted again once connections closed (no
  slot leak).
- **mTLS revocation (M1):** adding a throwaway client serial to the
  blocklist severed its live connection and rejected every new
  handshake, resumed sessions included; an unreadable list file kept
  the last good one (and kept rejecting); removing the entry
  re-admitted the certificate — zero restarts throughout.
- **extraEnv guard (X1):** `backend.extraEnv` carrying
  `TCDI_CONTROL_TOKEN` fails `helm template` with the pointer to
  `backend.controlToken.existingSecret`; `dev.enabled: true` still
  renders the escape hatch.
- **fd clamp (N1):** rc.1 Xvnc runs with soft `RLIMIT_NOFILE` 1000. A
  direct 450-connection burst stayed under the clamp and was fully
  accepted with no crash; a supplementary ~1050-connection burst —
  far above the gateway cap, directed at the runtime on a path the
  gateway never exposes — was refused `EMFILE` at the ceiling (82
  connections) and then tripped the residual documented under
  Availability below (a container restart, no memory corruption
  observed).
- **Smoke (S1):** `hack/e2e/smoke.sh --sign-out-everywhere` passed
  all 21 checks against the upgraded install; the v1.0.0 baseline had
  passed 20 with one documented quota SKIP.

Teardown then removed the install completely — every e2e namespace
gone, no persistent volumes left, the shared cluster identical to
its pre-install state.

**Development rollout.** The same rc.1 went out to the development
deployment through the normal GitOps path — a chart dependency bump
plus the cosign-verified digests, nothing else. The sync converged
in ~80 s: the schema version stayed at 23 (no migration ran), the
Workspace CRD generation was unchanged (no CRD apply), every pod
came up on the signed rc.1 digests with zero restarts and zero
workspace holds, and live sessions carried across. Both new backend
flags (`-session-stream-cap=32`, `-terminal-retention-days=30`) are
live, and the leader logged its first terminal-row retention sweep
within its first minute. The anonymous live round passed 10/10 —
including `/v1/metrics` answering 404 on the public host and all
five pinned security headers — and `hack/e2e/smoke.sh --anon-only`
passed 11/11.

**Supply chain.** The first runtime-train publish under the new
`attest-build-provenance` legs carried SLSA build provenance and
verified with `gh attestation verify`. The gate-failed-digest
cleanup was rehearsed end to end on real dispatches three times:
the third rehearsal (run 38153217638) resolved exactly its own run's
trees and deleted the 21 versions it had pushed — three per package
across the seven packages — with zero pre-existing versions touched,
zero residue and nothing signed, tagged or published. The leftovers
of the two earlier fail-closed rehearsals were removed afterwards
in a one-off maintainer cleanup — see SR-5-F3 below.

## Security

Each item below keeps its v1.0 review ID
(`docs/security/review-v1.0.md` §6) and its new status.

### `<component>.extraEnv` refuses dev-surface and chart-managed env names — SR-3-F2, accepted in v1.0 → fixed in v1.1 (#159)

`denyExtraArgs` refused the dangerous flags unless `dev.enabled`,
but `extraEnv` rendered verbatim and could carry the same flags'
environment equivalents, the env names of security-relevant
first-class chart values (live whenever the flag is not rendered),
or a duplicate of a chart-managed name that silently won. The render
now fails on all three classes — the deny table and upgrade impact
are under Upgrading. The check is deliberately a name enumeration,
not a `TCDI_*`/`PG*` prefix deny, so legitimate `extraEnv` tuning
stays possible under the 1.0 contract; the managed-name set is
derived from the chart's own env helpers, not a second
hand-maintained list. `dev.enabled: true` keeps the escape hatch.
**Residual:** an unlisted env name still renders verbatim — set
`extraEnv` with the same care as the guarded flags (SECURITY.md §B.5
recommends keeping it empty).

### Per-certificate revocation on the internal mTLS hop — SR-3-F5, accepted in v1.0 → implemented in v1.1 (ADR 0009, #158, #166)

The internal broker listener (`:9443`) gains an opt-in serial
blocklist. Before, distrusting one compromised operator or gateway
client certificate meant rotating the client-CA bundle, which drops
every client of the listener at once. With the backend flag
`-internal-revoked-list` (env `TCDI_INTERNAL_REVOKED_LIST`) or the
chart value `backend.tls.internal.revokedSerials.existingSecret`, a
mounted Secret carries the revoked `(issuer, serial)` pairs; a
listed leaf's TLS handshake is rejected — including on resumed
sessions — and its established connections are severed on the same
reload pass. The list hot-reloads on the proven poll+hash path (~90 s
propagation worst case), keeps the last-good list on a bad read, and
fails closed at boot when the flag is set but the file is unusable.

- New metrics: `tinycdi_internal_mtls_revoked_serial_total{listener}`,
  `tinycdi_internal_mtls_revocation_entries`,
  `tinycdi_internal_mtls_revocation_reload_errors_total`, plus the
  rate-limited `internal_mtls_revoked_cert` WARN line.
- Contract impact: none on `/v1` — the check is at the TLS layer,
  below HTTP. Chart values are additive with safe defaults; the
  default render is byte-identical (feature off).

**How to use it:** the operator runbook —
`docs/runbooks/mtls-cert-revocation.md` — walks serial → list entry
→ reload → verify rejected → reissue. ADR 0009's documented
recommendation is to pair the blocklist with shorter leaf lifetimes
(`certManager.duration: 168h`, `renewBefore: 24h` — shipped defaults
unchanged). **Residuals:** the check is server-side only — the
optional client-side (server-leaf) serial checks ADR 0009 sketches
for `opclient`/`brokerclient` are not wired (a compromised server
cert means a suspect CA — rotate the CA, do not blocklist it); and
the revocation of the internal CA itself is still rotation.

### `ClusterOnly` egress deprecation notice — SR-2-F8, posture stays accepted; default flips in v1.2 (#161)

`templates/NOTES.txt` now prints a WARNING at install/upgrade when a
seeded template uses `networkProfile: ClusterOnly` while
`runtime.networkProfiles.clusterOnly.egress*` is unset, announcing
the v1.2 restricted-egress default and naming the values to set —
see the opt-in-now / keep-today's-posture guidance under Upgrading.
The posture itself is unchanged and stays accepted for v1.1: a
`ClusterOnly` workspace may reach any pod that does not restrict its
own ingress; the #148 opt-in narrowing confines egress to
selector-matched namespaces/pods and optional ports. The chart's
operator-facing docs also state plainly that `Isolated` workspaces
keep cluster **DNS egress** — a deliberate unidirectional channel —
matching the API/CRD descriptions.

### Terminal-row retention for `connection_lease` / `launch_ticket` — SR-4-F5, listed open in v1.0 → fixed in v1.1 (#162)

Both session-layer tables are append-mostly: a ticket row is written
per launch and a lease row per redemption, and nothing ever removed
the rows after they died. On a long-lived deployment that growth
made every sign-out revocation scan and any future index build cost
more the older the install got — the SR-4-F5 residual from the v1.0
review.

The backend leader replica now runs an hourly retention sweep that
deletes rows terminal for longer than the configured window in
bounded batches (500 rows per statement, pausing between batches,
one sweeper via the Postgres leader lock):

- `connection_lease` rows in `revoked` / `expired` / `superseded`
  state, aged by `closed_at` (the terminal timestamp every
  transition writes).
- `launch_ticket` rows consumed, revoked or past `expires_at`, aged
  by the matching terminal timestamp.

Live leases and outstanding tickets are never touched, and no reader
depends on the deleted history — every sign-out, redeem,
cookie-resolve and post-restore path predicates on live/outstanding
rows only.

Configuration is additive with a safe default:

- flag `-terminal-retention-days` (env `TCDI_TERMINAL_RETENTION_DAYS`),
  default `30`; `0` disables the sweep.
- chart value `backend.retention.terminalRowDays: 30` — same
  semantic.

New metrics: `tinycdi_retention_rows_pruned_total{table}` and
`tinycdi_retention_last_success_timestamp_seconds` (documented in
`docs/runbooks/observability.md`); one INFO log line per pass
carries the counts. See `docs/runbooks/capacity.md` for the
bounded-growth note and `docs/security/review-v1.0.md` §6 for the
finding this closes. **Residual:** the sibling `workspace_revocation`
table still has no delete path — see Known limitations.

## Availability — the KasmVNC upstream crash boundary

The KasmVNC runtime ships no connection cap of its own. Xvnc
multiplexes every client connection with `select()`, whose `fd_set`
is bounded by `FD_SETSIZE` (1024): once the process's fd count
crosses that boundary — on the order of a few hundred concurrent
connections, at ~3 fds per connection plus baseline — its `FD_SET`
use writes past the stack-allocated set, corrupting the stack and
killing the X server. The pod restarts and every in-flight stream
resets at once; a reconnect storm used to surface at the gateway as
`502 upstream_unreachable` plus a runtime pod restart
(`docs/runbooks/capacity.md`). A pod inherits the host's
`RLIMIT_NOFILE` (~1M), so nothing stopped the fd count reaching the
boundary. v1.1 addresses the crash class in two layers:

- **Gateway: per-workspace concurrent upstream-stream cap** (#165).
  The session gateway bounds the number of live upstream connections
  a single workspace may hold through one replica:
  `-session-stream-cap` (default **32**, env
  `TCDI_SESSION_STREAM_CAP`, chart value `backend.sessionStreamCap`,
  minimum 1 — the bound cannot be disabled; choose a large value for
  runtimes that do not need it). Websocket streams and plain proxied
  requests count alike, and the bound is **per replica**: N replicas
  admit at most N × cap connections to one workspace. Over the cap
  the session origin answers `429` + `Retry-After: 1` +
  `{"error": "too_many_streams"}` — the session-listener limiter
  shape; the refusal is audited as `session.stream` denied and
  counted on `tinycdi_rate_limited_total{route="upstream_streams"}`,
  and a new unlabelled gauge `tinycdi_gateway_upstream_streams`
  reports the replica's in-flight upstream count. Compatibility:
  additive — new flag/env/chart value with a safe default; no
  existing behavior changes for traffic under the cap. The
  session-origin error code `too_many_streams` is additive to the
  session-listener error surface and, like `rate_limited` before it,
  lives outside the portal `/v1` error enum, which is unchanged.
- **Runtime: soft fd limit clamped below `FD_SETSIZE`** (#167).
  Both runtime entrypoints — `linux-base` (inherited by the
  linux-desktop and browser profiles) and the kasm adapter that
  drives unmodified `kasmweb/*` images — set a soft `RLIMIT_NOFILE`
  of `min(1000, hard)` before launching KasmVNC. Every fd Xvnc can
  hold stays `select()`-safe, so nothing — a client storm or a
  future path that bypasses the cap — can push an fd to the `FD_SET`
  boundary; excess connections fail `EMFILE` and are refused instead
  of corrupting the server. The hard limit is unchanged, so a debug
  shell can still raise it — and a pod whose hard limit is already
  below the target keeps its ambient bound rather than failing to
  boot (the clamp logs its result and never fails startup). No
  values, flags or API change — runtime image behavior only.

**Residual:** under sustained saturation a racing handshake thread
can still `exit(1)` on the `EMFILE`'d TLS-key open (the upstream
`fatal()` path) — a clean restart, not memory corruption. And a
direct burst far above the gateway cap (~1050 connections, well
past the 1000-fd clamp) can still crash Xvnc — a null dereference
after the `EMFILE` refusals; no memory corruption observed — and the
container restarts; that path is not reachable through the gateway.
The per-workspace gateway stream cap is the availability mitigation
on product paths.

## CI / supply chain

- **SR-5-F3 — gate-failed image digests are deleted by the same
  run; listed open in v1.0 → fixed in v1.1** (#164, rehearsal input
  #168). `images.yml`, `release.yml` and `runtime-images.yml` push
  images by digest before the trivy gate; a gate-failed publish run
  used to leave those unsigned manifests pullable-by-digest on GHCR.
  Each workflow now runs a `cleanup` job on failure that deletes
  exactly the versions the run pushed — every pushed index, its
  per-platform and attestation children and its referrers —
  resolved from the run's own `image-ref` artifacts
  (`.github/scripts/cleanup-failed-digests.sh`). Deletion is
  strictly run-scoped — a version goes only when it was created
  inside the run's window and is reachable solely from that run's
  tree; any candidate carrying a non-digest tag or reachable from a
  tagged manifest refuses the whole image. It never deletes a
  pre-existing version (a dedup'd identical rebuild's, or a
  published digest a ref points at), never sweeps unlabelled
  versions — GHCR stores published multi-arch children and cosign
  `sha256-*` artifacts unlabelled, and sweeping them breaks releases
  — and never touches the promote/publish leg's output, which may
  already be signed and tagged. Consumers keep the same guarantee:
  digests are pinned only out of signed manifests and verified with
  cosign first. A maintainer-only `fail_scan_for_rehearsal` dispatch
  input on `images.yml` (main only, default off) exists to rehearse
  the cleanup end to end; the procedure is in `.github/README.md`
  "Rehearsing the cleanup". Deletion was verified end to end in
  rehearsal run 38153217638 — the cleanup resolved exactly its own
  run's trees and deleted the 21 versions it pushed, with zero
  residue and nothing pre-existing touched. The unsigned, untagged,
  unreferenced versions the two earlier fail-closed rehearsals had
  left behind (42) were removed in a one-off maintainer cleanup,
  applied set-equal to a dry-run plan; published tags, signatures
  and attestations are unchanged.
- **Repo-protection drift detection** (#160).
  `setup-repo-protection.sh` now detects drift on the `release` and
  `runtime-train` environments beyond reviewer ids —
  `prevent_self_review`, `wait_timer` and the deployment
  branch/tag policy set, compared exactly: a missing entry plans a
  create, an unexpected entry plans a bounded delete (more than
  three aborts for manual review), and an unparseable or
  partially-paginated policies response fails the run closed instead
  of printing `ok`. The change counter now counts every planned or
  applied call, so the footer number equals the `WOULD:`/`RUN:` line
  count.
- **Runtime train approvals and attested train builds.** Under the
  v1.0 GA governance (review-v1.0.md §7) every `rt-*` train publish
  waits on a recorded `runtime-train` environment approval before
  the publish job runs — the durable record for the single-actor
  residual SR-5-F2. The publish job's `attest-build-provenance`
  legs mean train images carry SLSA build-provenance attestations
  alongside the cosign signature and SBOM attestation, verifiable
  with `gh attestation verify` — commands in `.github/README.md`
  "Verifying a release".
- **Release-candidate e2e smoke in the repo** (#163).
  `hack/e2e/smoke.sh` is an env-driven, API-level end-to-end smoke
  for a live deployment — anonymous surface, security headers, the
  scripted OIDC code+PKCE login, workspace lifecycle, quota
  refusal, logout and sign-out-everywhere — needing only `curl`,
  `jq` and reachability: no cluster access, no kubeconfig, no
  browser. It is committed so a release candidate can be re-verified
  from the tree alone; usage and the per-check rationale are in
  `hack/e2e/README.md`.

## Known limitations

The standing limitations of v1.0.0 still apply — see
`docs/releases/v1.0.0.md` ("Known limitations") for the full list.
Carry-forwards and new residuals for this release:

- **KasmVNC `EMFILE` residual.** Under sustained saturation a
  racing handshake thread can still `exit(1)` on the `EMFILE`'d
  TLS-key open (the upstream `fatal()` path) — a clean restart, not
  memory corruption. A direct burst far above the gateway cap
  (~1050 connections, well past the 1000-fd clamp) can still crash
  Xvnc — a null dereference after the `EMFILE` refusals; no memory
  corruption observed — and the container restarts; that path is not
  reachable through the gateway, where the per-workspace stream cap
  is the availability mitigation on product paths. The fd clamp
  removes the stack-corruption crash; it does not make the runtime
  unbounded.
- **Digest-cleanup TOCTOU window and uncovered legs.** The run
  window and run-tree reachability checks are check-then-act — a
  version could in principle gain a tag or a referrer between
  resolution and deletion; a small residual accepted for v1.1
  (`docs/security/provenance.md`). The cleanup also deliberately
  does not cover the promote/publish leg's output — that leg's
  digests may already be signed and tagged, so removal is an
  operator decision, not auto-deletion — and a workflow run that is
  stopped before its scan gate completes fires no cleanup at all,
  leaving its pushed digests in place (pullable by digest, unsigned;
  the consumption contract is unchanged: pin digests only out of
  signed manifests and verify with cosign first).
- **Client-side serial checks are not wired.** The ADR 0009
  blocklist is enforced on the internal mTLS listener only; the
  optional server-leaf serial checks it sketches for the
  `opclient`/`brokerclient` clients are not enabled — a compromised
  server cert means the internal CA itself is suspect, and the fix
  is CA rotation, not blocklisting.
- **`ClusterOnly` default still unrestricted until v1.2.** A
  `ClusterOnly` workspace may still reach any pod in any namespace
  on any port; confinement rests on destination-side ingress
  policies. Set `runtime.networkProfiles.clusterOnly.egress*` now —
  deployments that do see no behaviour change at the v1.2 flip (see
  Upgrading).
- **`workspace_revocation` rows are not pruned.** The table fences
  every revoked runtime generation `<= N` and has no delete path by
  design; the new retention sweep covers `connection_lease` and
  `launch_ticket` only. Its growth is bounded by one row per
  workspace revocation.
- Carried forward from v1.0.0: the audit stream is stdout JSONL
  (emission and shape guaranteed; delivery, retention and tamper
  evidence are the operator's log pipeline); per-prefix rate budgets
  still multiply across the prefixes a client holds (per-prefix
  limiting as designed); DNS egress is allowed on every network
  profile including `Isolated` by design; the single-maintainer
  residual (SR-5-F2) stays accepted, mitigated by the required
  `release`/`runtime-train` environment approvals; no independent
  audit yet — one is planned on the 1.x line; and for installs still
  ahead of the v0.4/v0.5 migrations, the non-concurrent
  `CREATE INDEX` builds of migrations 020/023 remain a
  quiet-window item per `docs/runbooks/upgrade.md`.
