# TinyCDI v0.3.1 — release notes

v0.3.1 is a patch release on v0.3.0: rollout-safety and correctness
fixes, a soft topology spread for workspace pods, and observability and
i18n additions. Merged since v0.3.0: #87–#94, #96–#98, #101.
No database schema, public API or CRD changes.

## What is new

**Scheduling**

- Soft topology spread for workspace pods (TOPO-1): every workspace pod
  now carries a `topologySpreadConstraint` — maxSkew 1 over
  `kubernetes.io/hostname`, `ScheduleAnyway`, scoped to the tenant
  namespace's runtime pods — preferring an even spread across pool
  nodes. It is a scheduling preference only and never blocks placement:
  a retained home PVC pinned by volume node affinity and a single-node
  pool still schedule. Set `runtime.topologySpread.enabled: false`
  (default true) to keep the pre-v0.3.1 packed-by-scoring placement
  (#87).

**Sessions and portal**

- Session-frame re-navigation counter (NAVTEL-1):
  `tinycdi_session_frame_reloads_total{dest}` counts document loads on
  a session whose lease already had a stream — the portal connection
  watch's lease-active reload and user reloads/new-tab loads, same tab
  only. Two exclusions keep it honest: the KasmVNC client's in-frame
  websocket retry (a bare `/websockify` upgrade) never counts, and a
  load carrying a different claiming tab id is a second-tab takeover,
  not a reload. `dest` is `iframe`, `document` or `other`; an overview
  dashboard panel is included (#89).
- Localized event and condition text (V3.14b): the portal renders the
  machine `reason` token of workspace events and conditions through
  the `en`/`vi` catalogs and keeps the server's message as secondary
  detail; an unknown token falls back to the server message (#90).

**Tests, CI and docs**

- Upgrade-drill readiness gate (FLAKE3): the quickstart upgrade job now
  gates its seeding phase on real routability — a ready EndpointSlice
  plus an edge HTTP code — not pod Ready, and dumps cluster diagnostics
  (restart counts, events, EndpointSlices, per-pod logs, the node
  journal) into the CI artifact on failure (#94, #98). The
  retained-disk smoke waits for the retained row to render before
  counting it (#98), the mock API stamps `createdAt`/`updatedAt` from a
  single clock read (FLAKE2, #92), and the upgrade smoke retries 5xx
  on portal navigation while its apply leg waits for all three
  rollouts (#93).
- Security review prep: `docs/security/threat-model.md` and
  `docs/security/test-inventory.md` inventory assets, actors, trust
  boundaries, current controls and the security-relevant tests ahead
  of the v1.0 review (#97).
- Sandboxed-runtime matrix (#101): `docs/compatibility.md` now carries
  a runtime × feature results table and a weekly workflow re-proves
  gVisor on kind — see Known limitations.

## Fixes

- Backend drain order (FX-R34): the pre-stop drain now waits
  `backend.drainPropagationDelay` (5 s default) after the readiness
  drop — streams keep flowing and new launches/upgrades are still
  served — before the graceful 1001 close tells clients to reconnect,
  so the in-frame retry lands on a sibling replica instead of back on
  the terminating pod, which would answer a retryable 503 and waste
  the client's one retry. The drain window (`backend.drainWindow`,
  8 s default) then holds the listeners for late reads. The chart
  fails the render when delay + window exceeds 20 s, keeping ≥ 4 s of
  the 24 s shutdown deadline for listener shutdown (#91).
- Frontend pre-stop drain (FX-R35): on SIGTERM `/healthz` fails at once
  and the pod keeps serving for `frontend.drainDelay` (8 s default,
  render-bound ≤ 20 s) while the endpoint removal propagates to
  kube-proxy / the edge — a frontend rollover no longer routes a
  sub-request to a pod that is already exiting (#93).
- Rate limits bound the aggregate, not one pod (RL-1): `-login-rate`
  and `-launch-rate` were per-pod budgets, so one key's effective
  limit multiplied by `backend.replicas`. The chart now passes
  `-rate-limit-replicas=backend.replicas` and every pod enforces
  rate÷N and burst÷N, each clamped to ≥ 1 — a configured rate smaller
  than the replica count yields ~N/min aggregate rather than silently
  disabling the limit, and 0 still disables it. The 10× per-IP
  OIDC-callback ceiling applies to the divided budget. Caveats: a
  rolling surge (N+1 pods) transiently overshoots to ~(N+1)/N× the
  bound, and an out-of-band `kubectl scale` leaves the rendered
  divisor stale until the next `helm upgrade` — an external HPA should
  pin `-rate-limit-replicas` to its `maxReplicas` via
  `backend.extraArgs` (#88).
- Expiry planner no longer loses a stop (OUTBOX-1): stop intents were
  marked drained when listed, before they were emitted — a leader loss
  in between lost the stop for good, and the
  (workspace, generation, reason) uniqueness barred re-recording it.
  A `stop_intent` row is now drained inside the same transaction that
  emits the outbox intent or proves it moot, so an interrupted sweep
  replays the intent on the next pass (#96).

## Upgrading from v0.3.0

The procedure is `docs/runbooks/upgrade.md`. No migration, no CRD or
public-API change — a helm upgrade with the new chart is enough.

- `-login-rate`/`-launch-rate` semantics change (RL-1): the flags now
  name the aggregate bound across `backend.replicas` — a value sized
  as a per-pod budget tightens to its 1/N share. Multiply by
  `backend.replicas` to keep the v0.3.0 effective budget (#88).
- New drain values have defaults — no action needed:
  `backend.drainPropagationDelay` (5 s), `backend.drainWindow`
  (8 s — a first-class value now; v0.3.0 tuned the window only via
  `backend.extraArgs -drain-window`) and `frontend.drainDelay` (8 s).
  The render fails when `drainPropagationDelay + drainWindow` exceeds
  20 s or `drainDelay` exceeds 20 s (#91, #93).
- `runtime.topologySpread.enabled` defaults to true: workspace pods
  created after the upgrade carry the soft spread (running pods are
  untouched); set it to `false` to keep the v0.3.0 packed-by-scoring
  placement (#87).
- During THIS upgrade, expect a few seconds of portal 5xx while the
  v0.3.0 frontend pods terminate — they predate the drain, so the
  edge can briefly route a sub-request (an `/assets/*` bundle,
  branding CSS) to a pod that is already exiting even after `GET /`
  answered 200; a browser reload once the rollout settles recovers
  it. From v0.3.1 on the frontend drains (`frontend.drainDelay`), so
  later upgrades do not have the window (#93).

## Known limitations

- Not independently security-reviewed; a full review is planned before
  v1.0. The review-prep material — threat model and security test
  inventory — now lives in `docs/security/` (#97).
- Sandboxed runtimes: gVisor verified on kind (desktop/terminal;
  Firefox ESR does not start under runsc — its WASM in-process
  sandbox's segue setup is unimplemented and the process aborts
  ~7–13 s in, while the desktop session itself stays healthy); Kata
  untested. `kubectl port-forward` to a runsc pod does not work —
  gVisor sockets live in netstack, not the kernel netns — so use the
  Service/pod-IP path, as the gateway does. The full matrix and the
  weekly CI re-proof are in `docs/compatibility.md` (#101).
- Per-user session limits were not exercised by the v0.3.0 soak
  (60 sessions across 20 users) and the API still has no per-user
  limit store — `userLimits` is absent, quota is tenant-scoped.
- Server-originated free text is English only: the portal now renders
  known event/condition `reason` tokens from the `en`/`vi` catalogs
  (#90), but message parameters and unknown tokens arrive in English.
- Reconnect tail after a full backend rollout: FX-R34 orders the drain
  so a client's retry lands on a live sibling (#91) and
  `tinycdi_session_frame_reloads_total` now measures how often the
  reload fallback actually fires (#89), but the tail was not
  re-measured at fleet scale — the v0.3.0 figure (p95 ~15 s at
  60 sessions, 1 s poll resolution) stands as the last measurement.
