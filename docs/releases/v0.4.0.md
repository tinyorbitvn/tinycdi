# TinyCDI v0.4.0 — release notes

v0.4.0 is a minor release on the v0.3 line: sign-out now revokes the
session's live desktop streams and outstanding launch tickets
(threat-model S17 closed), the login/launch rate limits enforce the
configured bound exactly across replicas through a Postgres-backed
shared window (ADR 0006 implemented), workspace events and conditions
carry structured `params` the portal renders localized, and the chart
gains per-route HTTPRoute annotations and route names. Merged since
v0.3.2: #105, #107, #109, #111, #112, #113. Schema migrations 019–021
run at backend startup — read "Upgrading from v0.3.x" first.

## What is new

**Rate limits**

- Postgres-backed shared windows for the login family and launch (ADR
  0006 option B, decided in v0.3.2 and implemented here): `-login-rate`
  and `-launch-rate` are now the EXACT aggregate bound across replicas,
  enforced by one `INSERT ... ON CONFLICT` upsert per check against the
  new `rate_limit_window` table (migration 021) — one row per (route,
  client key, minute window), so `-login-rate=30` + burst 10 lets one
  client draw 40 requests in a window however the traffic spreads
  across pods (#109). Three limiter families share the machinery:
  `login` (`/v1/login`, `/v1/auth/callback`, `GET /v1/session`),
  `callback_ceiling` (the 10× per-IP spray ceiling on the callback) and
  `launch` (`POST /v1/launch`). The divided per-replica token bucket
  stays on BOTH as the fail-open fallback during a store outage AND as
  a per-replica ceiling while Postgres is healthy — effective bound =
  min(shared window, local ceiling), so one pod never serves more than
  its 1/N share and a locally-refused key never reaches the store.
  Guardrails: every store check runs under a 500 ms deadline; a store
  error or timeout fails OPEN to the local bucket and opens a 10 s
  circuit breaker — checks skip the store entirely until it lapses,
  then exactly one request probes (single-flight; the rest keep their
  local verdict). The fixed-window edge admits up to ~2×(rate+burst)
  inside a span crossing a minute boundary — the same overshoot class
  the per-replica buckets had. Split mode (`-broker-url`, no database)
  keeps the divided in-memory limiter. New metrics:
  `tinycdi_rate_limit_store_errors_total{route}` counts real store
  failures only — checks skipped while the breaker is open never reach
  the store, so a sustained outage costs ~one increment per 10 s
  cool-down per limiter — and `tinycdi_rate_limit_store_degraded{route}`
  (gauge, 1 while the breaker is open); each limiter logs one line on
  fallback entry and one on exit, never per request. Expired window
  rows are deleted by the leader replica's periodic sweep (15-minute
  retention). Caveats: a key pinned to one pod by sticky load-balancing
  is bounded by that pod's 1/N ceiling even while the shared window has
  room, and during a store outage a configured rate below the replica
  count still clamps up to ~N/min aggregate (each pod's floor is 1/min)
  — never silently disabled.

**API and portal**

- Structured `params` on workspace events and conditions (B3-PARAMS):
  `WorkspaceEvent` and `WorkspaceCondition` may now carry `params`, a
  flat string map with the values the `reason`'s message interpolates —
  intent `revision`, stop `cause`, guard `skipReason`, the producing
  `condition`/`status`, the teardown `step` and the drain
  `budgetSeconds` (the full table is in `docs/lifecycle-reasons.md`)
  (#111). The portal renders its `en`/`vi` reason templates with these
  values localized — `TemplateUpdateSkipped` now reads e.g. "Workspace
  giữ nguyên revision template đã ghi nhận 7 (dung lượng nhỏ hơn)."
  instead of appending the English detail — and falls back to the
  server `message` when a token or a param is unknown, exactly as
  v0.3.x did. Stop intents recorded with an
  `idle_timeout`/`disconnect_timeout` cause now surface as their own
  `IdleTimeout`/`DisconnectTimeout` event reasons (previously a generic
  `StopRequested`; `max_duration` already mapped to
  `MaxDurationReached`). Additive only: `params` is optional everywhere
  (openapi `ReasonParams`), so mixed v0.3.x/v0.4 deployments degrade to
  the v0.3 rendering, and the operator-side condition-params annotation
  (`workspaces.cdi.tinyorbit.vn/condition-params`) is metadata only —
  no CRD change.

**Chart values**

- `gatewayApi.portalAnnotations` / `gatewayApi.sessionAnnotations`
  (CHART-3): annotations merged OVER the shared
  `gatewayApi.annotations` on the portal and wildcard-session HTTPRoutes
  — on a key collision the per-route value wins (e.g. a CDN proxy flag
  ON for the portal route, OFF for the long-lived-websocket session
  route). `gatewayApi.portalRouteName` / `gatewayApi.sessionRouteName`
  rename the two HTTPRoute objects for GitOps wrappers that pair
  hand-written routes by name; the defaults (`portal`, `session`)
  render the names every earlier chart produced (#113).

**Tests and CI**

- Partitioned-cookie e2e (B6-PART): a new kind quickstart variant
  installs with `backend.sessionCookieMode: partitioned` (SameSite=None;
  Secure; Partitioned — CHIPS, the mode a deployment needs when portal
  and session domains sit on different registrable domains) and drives
  `smoke/partitioned.spec.ts` against it — login, create, the embedded
  Connected session, a backend rollout with in-frame reconnect,
  stop/start and logout — asserting the real Set-Cookie attributes and
  that the session listener rejects a cookie whose lease is dead. It
  runs on the same PR paths plus the weekly schedule and is not a
  required check. Tests and CI only (#112).

## Fixes and security

- Sign-out revokes the session's reach over the desktop layer — S17
  closed (B2): `POST /v1/logout` deletes the portal session row first —
  visible to ticket redemption's session check as early as possible —
  then, in one store transaction, revokes every active
  `connection_lease` minted under the session's digest and every
  still-outstanding launch ticket it issued (#107). A revoked lease
  fails the owning replica's next renew, so the bound stream closes
  within one renew cycle (10 s at the default `-renew-interval`); a
  replayed workspace-host cookie resolves to the revoked lease and gets
  a 401 on any replica; a ticket in flight at sign-out can never mint a
  replacement lease — redemption re-checks the session row, and the
  revoke's ticket UPDATE serializes against in-flight redemptions. The
  revoke is best-effort and bounded (5 s, detached from the request's
  cancellation): a store failure is logged, counted on
  `tinycdi_session_revocations_total{result="error"}` and audited
  (`session.revoke`) but never fails the sign-out — the portal cookie
  is cleared and the session destroyed regardless. Migration 020 adds
  the two partial `portal_session_digest` indexes backing this; the
  threat model now marks S17 Implemented.
- `sessions.csrf_token` dropped (migration 019, B1): the contract half
  of the expand/contract migration 017 started — no v0.3.x binary names
  the column, so it can finally go. Upgrade-path notes below (#105).
- Measured on the v0.4.0-rc.1 e2e install (two replicas, upgraded from
  v0.3.2 with a live session): sign-out closed the live desktop stream
  0.4–0.6 s after logout in 3/3 runs (WebSocket close ~7 s — inside the
  10 s renew cycle), a replayed workspace-host cookie got 401 on both
  replicas, and a launch ticket minted before sign-out could not be
  redeemed. An anonymous burst spread across both replicas was admitted
  exactly to the configured aggregate (rate + burst — not 2×), 20
  authenticated lanes saw no 429, and a 38 s database brown-out kept
  login/launch answering in ≤ 0.52 s (fail-open to the local ceiling)
  with the shared window resuming after the 10 s cool-down probe.

## Upgrading from v0.3.x

The procedure is `docs/runbooks/upgrade.md`; this upgrade carries
schema migrations, so read it and the points below before running it.

- **Upgrade ONLY from v0.3.x — never v0.2.x → v0.4 directly.** A
  still-running v0.2 replica names `sessions.csrf_token` in every
  session `SELECT`/`INSERT` and fails the moment migration 019 drops
  the column; every backend must be on v0.3.x before the v0.4 schema
  lands. The drop itself is rolling-upgrade safe from v0.3.x (no v0.3
  binary names the column).
- **Back up the database first** (`pg_dump` per
  `docs/runbooks/backup-restore.md`). Migrations 019–021 are
  forward-only — there is no down migration, and `helm rollback` does
  not undo them: rolling back after the upgrade restores the old
  binaries against the new schema (019's column stays dropped), so a
  real rollback is restoring the pre-upgrade `pg_dump`. Never roll back
  to v0.2 after the v0.4 upgrade without restoring the dump.
- **Index builds briefly block writes.** Migration 020's plain
  `CREATE INDEX` builds on `connection_lease` and `launch_ticket` hold a
  write-blocking lock while running (`CONCURRENTLY` cannot run inside
  the migration transaction) — on large installs run the upgrade in a
  quiet window.
- **Rate-limit semantics change (ADR 0006).** `-login-rate`/
  `-launch-rate` now name the exact aggregate bound the shared Postgres
  window enforces — no more divisor approximation. `-rate-limit-replicas`
  changes meaning: it is now the divisor of each pod's LOCAL ceiling —
  the cap no pod may exceed while Postgres is healthy and the fail-open
  limit during a store outage — not the aggregate. The chart still
  renders `-rate-limit-replicas=backend.replicas`; an external HPA
  should pin it to `maxReplicas` via `backend.extraArgs` (it renders
  after the chart's value and wins) so the degraded-mode bound holds at
  full scale. A mixed-version rollout applies one enforcement or the
  other per request — the aggregate bound may differ by the per-replica
  share for the seconds the rollout spans.
- **Event reason/id change for idle/disconnect stops.** Stop events
  recorded for `idle_timeout`/`disconnect_timeout` causes now carry the
  reason `IdleTimeout`/`DisconnectTimeout` instead of `StopRequested`;
  their event ids change accordingly — clients grouping by `reason`
  should add the new tokens. The recorded `cause` is still carried in
  `params.cause`, so the `StopRequested` + cause detail is not lost
  (#111).
- **New chart values default to the previous render** — no action
  needed: `gatewayApi.portalAnnotations` / `.sessionAnnotations`
  default to `{}` and `gatewayApi.portalRouteName` /
  `.sessionRouteName` default to `portal`/`session`, so an unchanged
  values file renders byte-identical routes (#113).
- `params` on `WorkspaceEvent`/`WorkspaceCondition` is optional and
  additive: older clients ignore it and v0.3.x replicas interoperate
  unchanged; the condition-params annotation is metadata only, so no
  CRD or client action is needed (#111).
- Measured on the same e2e upgrade: the live session dropped ~1.5 s and
  resumed in-frame (same lease, no re-login); migrations 019–021
  applied to a restored copy of a production-shaped database with
  identical row counts, and restoring the pre-upgrade dump returned
  schema 18 with identical counts — the documented restore path works.

## Known limitations

- Not independently security-reviewed; a full review is planned before
  v1.0. The review-prep material — threat model (S17 now marked
  Implemented) and security test inventory — lives in
  `docs/security/`.
- "Sign out everywhere" is not yet a feature: `POST /v1/logout` revokes
  the signing-out portal session's leases and tickets (S17); a user's
  other live portal sessions — other browsers, other devices — stay
  signed in until they expire or are signed out individually.
- Per-user session limits are deferred to v0.5: the API still has no
  per-user limit store — `userLimits` is absent, quota is
  tenant-scoped.
- Sandboxed runtimes: gVisor verified on kind (desktop/terminal;
  Firefox ESR does not start under runsc — its WASM in-process
  sandbox's segue setup is unimplemented and the process aborts
  ~7–13 s in, while the desktop session itself stays healthy); Kata
  untested. `kubectl port-forward` to a runsc pod does not work —
  gVisor sockets live in netstack, not the kernel netns — so use the
  Service/pod-IP path, as the gateway does. The full matrix and the
  weekly CI re-proof are in `docs/compatibility.md`.
- Server-originated free text is English only: the portal renders known
  event/condition `reason` templates — with their `params` — from the
  `en`/`vi` catalogs (#90, #111), but unknown tokens and other server
  messages still arrive in English.
