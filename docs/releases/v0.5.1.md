# TinyCDI v0.5.1 — release notes

v0.5.1 is a patch release on v0.5.0 carrying the fixes from the
internal security review ahead of v1.0 — headlined by moving the
per-workspace template snapshot that drives pod building onto
operator-authoritative storage (`status.templateSnapshot`, a CRD
change), with hardening across the session listener, the gateway
proxy, the rate-limit keyspace, sign-out, the portal idle window,
the internal control API, the chart and the supply chain — plus the
routine dependency train. Merged since v0.5.0: #131–#135, #142–#150;
dependency updates #136–#141. **The `workspaces` CRD gains
`status.templateSnapshot` — read "Upgrading from v0.5.0" first: a
plain `helm upgrade` does not update CRDs.** There is no database
migration.

## Security

**Operator-authoritative template snapshots** (#146, S30)

- The immutable per-workspace template snapshot that drives pod
  building used to live in the
  `workspaces.cdi.tinyorbit.vn/template-snapshot` annotation —
  ordinary Workspace metadata. The snapshot was integrity-checked,
  but its live-object provenance check passed vacuously when the
  source template was missing or rotated, and the confinement
  annotations (seccomp/AppArmor) sat outside the checked hash — so a
  principal able to write Workspace objects could write a snapshot
  that made the operator build pods from an arbitrary spec: image,
  command, placement, `runtimeClass`, resources, egress profile,
  `localhost/*` seccomp name. The snapshot now lives in
  **`status.templateSnapshot`** — writable only through the
  `workspaces/status` subresource, which RBAC grants to the operator
  service account alone. The operator records it itself from the
  live template `spec.templateRef` resolves to, never from the
  annotation, and keeps **mirroring** it to the annotation for
  readers — the annotation is still consumer-visible but nothing
  trusted reads it. A workspace with no status record and no
  resolvable live template fails closed: no pod,
  `Degraded`/`TemplateInvalid`, one edge-triggered Warning event.
  The broker's expiry planner reads status first too, and a
  workspace held for an unprovable revision gets lifecycle caps from
  the **stricter of the resolved template and the chart defaults** —
  an annotation carrying inflated caps can never stretch a held
  session. The upgrade-time adoption contract is under Upgrading.

**Start-time template guard + seccomp validation** (#150, S37/S38)

- The template-family guard (`imageUpdate: OnStart`) that refuses an
  incompatible re-point at the next start used to compare only
  runtime/experience/data-policy/storage — a published revision
  could silently move an existing workspace's `networkProfile`
  (egress boundary), `clipboardPolicy`, `adapter`, `hostUsers`,
  placement or the seccomp/AppArmor profile annotations. Each is now
  an exact-match dimension: any change — in either direction,
  "tightening" included — records `TemplateUpdateSkipped` with a
  reason naming the field (`network-profile-changed`,
  `clipboard-policy-changed`, `adapter-changed`, `host-users-changed`,
  `placement-changed`, `seccomp-profile-changed`,
  `apparmor-profile-changed`) and the workspace keeps its recorded
  revision. Image/revision freshening still flows.
- The `seccomp-profile` template annotation is validated like
  `apparmor-profile`: `runtime/default` or `localhost/<clean
  relative path>` (no `.`/`..` segments, whitespace or backslashes —
  subpaths like `profiles/chromium-userns.json` stay valid);
  anything else — `unconfined`, a bare `localhost/`, a traversal —
  rejects the template before any child object exists. The check
  runs at pod build, at snapshot **admission** (an out-of-policy
  live template is never recorded — `Degraded`/`TemplateInvalid`),
  and at recorded-snapshot verification.

**Session listener** (#147, S31–S33)

- A request carrying a session cookie the serving replica has never
  seen was the only pre-auth path that spent store reads — a
  `session_digest` lookup plus an `EXISTS` probe on miss — and each
  unique cookie minted its own singleflight entry, so a random-
  cookie spray converted request rate directly into Postgres reads.
  The unknown-cookie path now sits behind a **local** per-client
  token bucket consulted before any store read —
  `-session-lookup-rate` (300/min, burst 120 **per replica**;
  `0` disables). Refusals answer `429` + `Retry-After`, count
  `tinycdi_rate_limited_total{route="session_lookup"}` and audit
  `session.lookup` denied. Deliberately local-only — a shared
  Postgres window would spend the reads it exists to prevent.
  Valid-but-uncached cookies draw tokens too (a backend rollout
  makes every session uncached), so the burst absorbs a reconnect
  storm — see the NAT sizing rule under Upgrading. Cookies a live
  local session owns, cookie-less requests and rehydrated sessions
  never consult the limiter.
- Sessions abandoned between ticket redeem and the 303 delivery used
  to pin their workspace indefinitely — session registration and the
  renew loop started before the `Set-Cookie` was written, so a
  client that dropped in that window left a session no browser holds
  renewing the lease (`IssueTicket` → `409 CONNECTION_IN_USE` for
  the next launch). Sessions now mint *unattached* and the first
  request admitted on their own host attaches them; a session still
  unattached at `-unattached-session-ttl` (default 90 s) is reaped —
  the decision and the lease revoke run under one session lock, so a
  completed attach can never be revoked, the revoke is skipped when
  a sibling replica already claimed the stream, and a failed revoke
  still kills the session (the lease then lapses inside one lease
  TTL).
- `Cross-Origin-Opener-Policy: same-origin` is pinned on every
  session-listener response, matching the frontend's pin; an
  upstream-supplied COOP is stripped so a tenant-controlled runtime
  cannot weaken it. Framing is unaffected — embeddability stays
  governed by CSP `frame-ancestors`.

**Rate-limit client keys** (#132, #145)

- IPv6 client keys fold to the **/64 prefix** — the smallest block
  one subscriber is delegated — so temporary/privacy-address
  rotation or /128-hopping inside one prefix draws a single budget
  instead of minting a fresh bucket per address; the IPv4-mapped
  spellings (`::ffff:a.b.c.d`, any notation) unify with the native
  v4 key, and IPv4 stays per-/32. The corollary: all hosts inside
  one shared /64 — a LAN segment, subscribers an ISP gives a single
  prefix — share one budget. The fold applies to limiter keys only:
  the forwarded `X-Forwarded-For`/`Forwarded`/`X-Real-IP` rebuild
  toward the runtime and audit attribution carry the client's real,
  unmapped-but-unfolded address. Socket-peer paths canonicalise
  identically, and one canonical string keys the local buckets and
  the shared Postgres window rows end to end.
- A selected `X-Forwarded-For` entry that is not a plain IP — a
  garbage token, hostname, `unknown`, a zoned IPv6 literal or an
  `addr:port` form — can never become a limiter key: it collapses
  to the verified socket peer, so a client whose own bytes reach
  the selected slot shares one bounded peer bucket instead of
  voiding every per-key budget (and minting a `rate_limit_window`
  row per sprayed key). The forwarded-header rebuild can never
  carry non-address bytes either. The audit-coverage pin was
  hardened alongside into a mounted-mux replay: one request driven
  through every mutating and `/v1/admin/` spec route must emit
  exactly one domain event with the table's action, so a plainly
  mounted (or wrapped-and-discarded) route fails the build.

**Gateway proxy header handling** (#142, S18)

- The gateway injects `Authorization`, `Sec-WebSocket-Origin` and
  the rebuilt forwarding chain toward the runtime — but the stdlib
  reverse proxy ran its `Director` *before* the hop-by-hop strip,
  and that strip deletes every header the client's `Connection:`
  token list names. A session holder sending
  `Connection: upgrade, authorization, ...` therefore reached the
  runtime's auth layer with none of the injected headers —
  completely unauthenticated — and the forwarded client-address
  chain arrived degraded. Injection now runs in the proxy's
  `Rewrite` hook, after the strip, so no client token list can
  remove the injected headers; client `Connection` tokens are
  canonicalised to `upgrade`/`keep-alive`/`close` with drops counted
  on `tinycdi_gateway_connection_tokens_dropped_total` and logged
  at most once a minute per route.
- The whole client-supplied forwarding and vendor client-address
  set — `X-Forwarded-*`, `X-Original-*`, `X-Rewrite-Url`,
  `Forwarded`, `X-Real-Ip`, `Via`, `X-Client-Ip`, `True-Client-Ip`,
  `CF-Connecting-Ip`, `X-Cluster-Client-Ip`, `X-Envoy-*` — is
  stripped from one table before the verified rebuild (variants
  like `X-Forwarded-Host` previously reached the tenant-controlled
  runtime verbatim), and the per-session upstream transport gains
  `ResponseHeaderTimeout: 30s`, so a runtime that accepts TLS then
  stalls can pin neither request goroutines nor the session's
  single upgrade admission. Established websocket streams are
  unaffected by construction: the 101 *is* the response headers.

**Portal idle timeout honoured** (#133)

- Portal sessions carry a sliding idle timeout, but the SPA polls
  `GET /v1/workspaces*` every 8–10 s on a visible tab — and those
  routes sat behind sliding auth, so an open but unattended tab
  kept the session alive forever. Every cookie-authenticated `GET`
  now mounts passive auth (`Peek`, no slide); only mutations slide —
  including the new **`POST /v1/session:touch`** activity beat
  (passive auth + CSRF, the slide applied explicitly only *after*
  the token check so a cookie-only request never earns one;
  audited `session.touch`; the SPA fires it on `pointerdown`,
  `keydown` and route changes, throttled to one beat per 60 s,
  never from timer polls). Desktop streams honour the same window:
  the lease redeem/renew/rehydrate session re-checks now require
  `last_seen_at` inside the idle window, so an idle-dead session's
  lease is revoked on the spot — the stream dies within one renew
  cycle instead of outliving its session. Renew deliberately does
  **not** slide the window, or a connected-but-idle stream would
  pin the session open again. Net idle semantics: no user
  interaction **and** no desktop input for the whole window.
- Desktop input is now scoped to the **bound** session: RFB input
  used to slide every session of the principal; the touch lands on
  the lease's `portal_session_digest` only (NULL-digest legacy
  leases keep the principal-wide fallback so pre-upgrade streams
  survive a rolling deploy).

**Sign-out fails closed** (#131)

- `POST /v1/logout` used to log a session-store `Delete` error,
  expire the cookie and answer `204`/`200` — while the server-side
  session stayed live and a copied cookie kept working. The session
  delete is now the ordering's point of no return: on a store error
  the handler answers retryable **`503 UNAVAILABLE` +
  `Retry-After`** and tears nothing down — no cookie expiry, no
  lease/ticket revoke — so the refusal's claim matches reality and
  a retry (the operation is idempotent) completes the destroy.
  Delete-first is kept deliberately: revoking material first would
  leave a live session with dead streams on delete failure, and
  expiring the cookie would tell the browser it is signed out
  while the session still works. `POST /v1/me/sessions:revoke-all`
  already fails closed (one transaction; `500` + `retryable`,
  cookie expired only after commit) and keeps that shape. The
  portal's sign-out item surfaces the refusal and offers retry.

**Auth hardening** (#134, S25–S27)

- The post-logout redirect (`oidc.postLogoutRedirect`) and the
  discovered `end_session_endpoint` must now be absolute **https**
  URLs — `http` is accepted only for loopback hosts (`localhost`,
  `127.0.0.0/8`, `::1`, strict parse — mapped/octal spellings do
  not count), matching the dev plain-http-on-loopback IdP
  convention. The chart schema already required `^https://`; the Go
  side now matches it.
- Two dead/misleading config knobs are removed rather than wired:
  `AuthConfig.IdleTimeout` was defaulted but never read (the
  session store owns the idle window — `-session-idle`), and
  `AuthConfig.AllowedTenants` was enforced but no flag/env/chart
  path could ever populate it (`-required-groups` remains the
  supported login gate). No reachable behaviour changes.
- `POST /v1/connections` decode failures now answer `400` with the
  generic `"invalid request body"` — the decoder detail is logged
  server-side with the request id, and trailing data after the
  first JSON document is rejected.

**Internal control API** (#143, S28/S29)

- `POST /internal/v1/broker/workspaces/{uid}/revoke` accepted an
  unbounded `runtimeGeneration` written verbatim into
  `workspace_revocation` — whose rows fence every generation `<= N`
  and have no delete path — so a far-future value (2^62) bricked
  the workspace permanently. The broker now refuses any generation
  beyond the recorded bound (the mint counter, plus one of
  observed-but-unprojected slack) with `400 INVALID_REQUEST`; calls
  within the bound stay idempotent and an unknown workspace keeps
  its no-op shape.
- Requests refused by the internal mTLS listener's `identify`
  middleware were never logged — no-cert, empty-CN and
  SPIFFE-mismatch rejections left no record at the boundary. Every
  refusal now counts on
  `tinycdi_internal_auth_failures_total{reason}` and emits a
  rate-limited warn line (1/s, burst 10, per reason class) carrying
  request id, method, peer and the SEC-41-redacted path — raw
  paths embed lease ids, which are bearer material on this
  listener. Certificate/SAN/key material is never logged.

**Chart hardening — all opt-in, defaults unchanged** (#148, S34/S35;
#149, S36)

- `runtime.networkProfiles.clusterOnly.egressNamespaceSelector` /
  `egressPodSelector` / `egressPorts` render the new operator flag
  `--runtime-clusteronly-egress`, which rewrites every
  `ws-<uid>-boundary` `ClusterOnly` egress rule to a single
  selector-matched peer (+ports) — confining workspace egress to
  e.g. the managed tenant namespaces instead of any pod in any
  namespace on any port. The narrowing can never widen past pod
  destinations (a ports-only value keeps an all-namespaces *pod*
  peer, so external IPs stay denied); DNS egress is untouched, and
  all-empty values render no flag — the default render is
  byte-identical to v0.5.0 (pinned by a whole-render byte golden in
  CI). Spec-drift reconcile rolls the change out to existing
  workspaces.
- `managedNamespaces[].namespaceQuota` renders a `ResourceQuota`
  (`tinycdi-workspace-quota`: summed requests/limits, pod/PVC/
  Service counts) and/or a `LimitRange`
  (`tinycdi-runtime-defaults`) into exactly the listed namespaces —
  apiserver admission then bounds the blast radius of any pod spec
  that reaches the operator, independent of the API-layer tenant
  quota. Keep the ResourceQuota aligned with `quota.workspaces` —
  sizing it below the tenant quota leaves new workspaces Pending.
- `admissionPolicy.enabled` (default **off**, Kubernetes >= 1.30 —
  already the chart's `kubeVersion` floor) renders a
  `ValidatingAdmissionPolicy` + binding that denies create/update
  of `Workspace` objects adding, changing or removing the
  `template-snapshot` mirror annotation for everyone except the
  operator service account (plus optional
  `admissionPolicy.extraAllowedUsernames` for restore tooling). A
  matching `config/admissionpolicy/` kustomize sample ships for the
  non-Helm path. Nothing trusted reads the annotation (S30), so
  this is defence-in-depth for consumers that still read the
  mirror.

**Supply chain** (#135)

- `runtime-images.json` — the manifest deployments pin runtime
  digests from — was the only unsigned artifact in the release
  chain; the image train now `cosign sign-blob`s it and attaches
  `runtime-images.json.sigstore.json` on every `runtime-*` release,
  with the exact `cosign verify-blob` command documented where the
  manifest is consumed (`docs/images.md`,
  `docs/runbooks/upgrade.md`, `.github/README.md`).
- The scan jobs' `SCAN_REF` writes to `$GITHUB_ENV` are validated
  against the strict `ghcr.io/...@sha256:<64hex>` form first — a
  malformed ref (a newline could inject arbitrary env vars) fails
  the job instead.
- The train publish job gains SLSA build-provenance attestation
  legs matching the release workflow's, gated on a repo variable
  (`TRAIN_ATTESTATIONS_ENABLED`, default **off** — enable it only
  after verifying on a tag build).
- The packaged Helm chart and the static release binaries ship
  dedicated SPDX SBOMs (`sbom-chart.spdx.json`,
  `sbom-binaries.spdx.json`), produced, validated, checksummed and
  signed like every other release asset.
- The threat model and security test inventory now record the review
  items S25–S38 with their fixes and pinning tests
  (`docs/security/`).

## Upgrading from v0.5.0

The procedure is `docs/runbooks/upgrade.md`; this upgrade carries a
CRD change, so read it and the points below before running it.

- **Apply the CRDs first.** The `workspaces` CRD gains the optional
  `status.templateSnapshot` field — additive, so existing objects
  stay valid and a still-running v0.5.0 binary ignores it. GitOps
  tooling that applies `crds/` handles this automatically; a plain
  `helm upgrade` does **not** upgrade `crds/` — apply them first:
  `kubectl diff -f deploy/helm/tinycdi/crds/` then `kubectl apply
  -f deploy/helm/tinycdi/crds/`.
- **No database migration** — the v0.5.0 schema is unchanged.
- **Rolling-window safety.** The operator's leader-election Lease
  hands reconcile to exactly one pod at a time, so there is no
  window where a v0.5.0 and a v0.5.1 operator reconcile the same
  workspace (a `replicas: 1` install simply rolls the one pod, as
  every upgrade).
- **Silent adoption for current workspaces.** On its first
  reconcile of each workspace the new operator establishes
  `status.templateSnapshot` — the annotation is never consulted,
  not even as a lookup hint. A running workspace whose pod provably
  matches the live revision `spec.templateRef` resolves to (a
  field-for-field normalized rebuild, or the pod's own stamped
  template identity on pods the new operator built) is adopted
  silently: the record is written **from the live revision
  object**, identity stamps are backfilled onto the running pod,
  and the pod is never touched — no `Degraded`, no restart.
- **Expected holds.** A running workspace whose pod revision cannot
  be proven — sessions started **before the last template rollout**
  (the pod was built from a revision since rotated, pruned or
  republished), webhook-altered pods, and pods built from a forged
  snapshot — holds `Degraded`/`TemplateRevisionGone` with its pod
  left running untouched, plus one edge-triggered Warning event.
  When the revision proves fine but the live template's content
  fails admission (an out-of-policy `seccomp-profile`), the hold is
  `Degraded`/`TemplateInvalid` instead — same single Warning, pod
  untouched. Either hold clears with a stop/start, which
  re-snapshots the live template. While held, the broker's expiry
  planner ignores the annotation entirely — lifecycle caps come
  from the **stricter of the live template and the chart
  defaults**. **If annotation tampering is suspected, stop the
  suspect workspaces before upgrading** — a forged-spec pod cannot
  prove its identity and would hold `TemplateRevisionGone`
  afterwards anyway; stopping it first is the clean path, and
  nothing forged is ever adopted into status. Post-upgrade check —
  an empty name with `Degraded`/`TemplateRevisionGone` is the
  expected hold, cleared by a stop/start:

  ```
  kubectl -n <tenant-ns> get workspaces \
    -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.templateSnapshot.name}{"\n"}{end}'
  ```

- **New flags and defaults** (settable via `backend.extraArgs` or
  env): `-session-lookup-rate` (`TCDI_SESSION_LOOKUP_RATE`;
  300/min, burst 120 **per replica**, `0` disables) bounds
  directory lookups for unseen session cookies — and
  `-unattached-session-ttl` (`TCDI_UNATTACHED_SESSION_TTL`; ~90 s)
  reaps sessions that never admitted a request. **NAT sizing
  rule:** every valid-but-uncached cookie draws a lookup token too,
  and a reconnecting client costs ~2 tokens (the frame document
  load plus the `/websockify` upgrade), so size for ~2 × concurrent
  reconnecting clients per replica — the default burst covers ~60
  concurrent reconnects from one client address, and refused
  clients see `429` + `Retry-After` and retry. See
  `docs/runbooks/capacity.md` ("Sign-in rate limits and NAT").
- **Rate-limit key-format change — one-time, no migration.** IPv6
  client keys move from per-address to per-/64; IPv4 keys are
  unchanged. Window rows written under the old format expire inside
  their minute window, so an IPv6 client mid-window at upgrade time
  gets at most one fresh window's budget. Operators with many users
  behind one shared /64 (a single-prefix ISP, one LAN segment) may
  see those users share one budget where they previously drew one
  each — the flags are unchanged.
- **Behaviour changes to expect:** `POST /v1/logout` can now answer
  retryable `503` instead of always succeeding — clients should
  treat it as "not signed out, retry". The portal idle window now
  actually closes: a session with no interaction and no desktop
  input for the whole `-session-idle` window expires — previously
  background polls kept it alive indefinitely, so some long-open
  tabs will sign out for the first time. `POST /v1/connections`
  returns a generic decode-error message. The runtime no longer
  receives client-supplied `X-Forwarded-*`/vendor address headers —
  it gets the gateway-rebuilt chain only — and client `Connection:`
  token lists are canonicalised on the proxy hop.
- **New metrics and audit events:**
  `tinycdi_gateway_connection_tokens_dropped_total` (#142),
  `tinycdi_internal_auth_failures_total{reason}` (#143 — a nonzero
  rate is refused internal API calls, worth alerting on),
  `tinycdi_rate_limited_total{route="session_lookup"}` (#147);
  audit actions `session.touch` (#133) and `session.lookup` (#147,
  emitted on denials). If your log pipeline filters on `action`,
  widen it.
- **New opt-in chart values — defaults off, no action needed:**
  `runtime.networkProfiles.clusterOnly.*` (ClusterOnly egress
  narrowing), `managedNamespaces[].namespaceQuota`
  (ResourceQuota/LimitRange), `admissionPolicy.enabled`
  (ValidatingAdmissionPolicy for the mirror annotation).
- **Additive API surface** — no client action needed:
  `POST /v1/session:touch`; `POST /v1/logout`'s documented `503`.
- **Rollback to v0.5.0 is safe.** The `template-snapshot`
  annotation mirror stays fully populated, so a v0.5.0 operator
  (which reads only the annotation) keeps converging the same
  recorded revision and ignores the new status field entirely — do
  not "un-apply" the v0.5.1 CRD, the extra field is inert under
  v0.5.0.

## Known limitations

- The standing limitations of v0.5.0 still apply — see
  `docs/releases/v0.5.0.md` ("Known limitations") for the full
  list; the notable carry-forwards for this release: the audit
  stream is stdout JSONL (emission and shape guaranteed; delivery,
  retention and tamper evidence are the operator's pipeline), and
  per-prefix rate budgets still multiply across the prefixes a
  client holds — a client holding several /64s or several egress
  addresses gets a budget per prefix (per-prefix limiting as
  designed).
- **Skip reasons are server-side English.** The two new hold
  reasons render localized (`en`/`vi`), but the seven new
  `TemplateUpdateSkipped` reason tokens and other server-originated
  messages arrive in English — the portal's reason-token catalogs
  cover the curated set only, as before.
- Two residual items documented in `docs/security/threat-model.md`
  are accepted for this release and planned for a later one:
  **per-certificate revocation** on the internal mTLS hop — there
  is no CRL/OCSP/serial blocklist, so removing trust in one client
  certificate means rotating the client CA bundle (dropping every
  client); short-lived certs via cert-manager remain the mitigation
  and rotation is the revocation mechanism. And **`extraEnv` vs the
  chart's render guards**: the `denyExtraArgs` guard refuses
  dangerous flags unless `dev.enabled`, but `<component>.extraEnv`
  is rendered verbatim and can carry those flags' environment
  equivalents — set `extraEnv` only with the same care as the
  guarded flags (an env-name deny-list is the planned fix).
