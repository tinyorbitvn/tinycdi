# TinyCDI v0.5.0 — release notes

v0.5.0 is a minor release on the v0.4 line: "sign out everywhere" ends
every portal session a principal holds in one tenant — all devices, the
calling one included — and revokes its live desktop streams and
outstanding launch tickets in one transaction (ADR 0007; threat-model
S19), tenant administrators can cap concurrent running workspaces per
principal (migration 022), every mutating and admin API route now emits a
dedicated audit event, lease renew/attach re-validates the bound portal
session so a database-restore-resurrected lease dies on first touch (S17
defence-in-depth), the disaster-recovery runbook grows a verified
Postgres-only-restore procedure backed by a `backend post-restore`
one-shot tool, intent-fence drift is surfaced as an `IntentBehind`
condition instead of dropped silently, threat-model S18 is closed by
analysis (ADR 0008), and the chart refuses two deploy-time
misconfigurations. Merged since v0.4.0: #117–#125, #127, #128. Schema
migrations 022–023 run at backend startup — read "Upgrading from v0.4.x"
first.

## What is new

**Sign out everywhere** (#117, ADR 0007)

- `POST /v1/me/sessions:revoke-all` — the principal-scoped bulk variant of
  `POST /v1/logout`, behind the same RequireAuth + `X-CSRF-Token` pair and
  the session-keyed login-family rate limit. One store transaction per
  principal, in the caller's tenant only, in the same lock order the other
  session-layer mutators use (tickets → sessions → leases): every
  outstanding launch ticket of the principal is revoked (waiting out any
  in-flight redemption on its `FOR UPDATE` row lock), every portal session
  row is deleted — the calling session included, there is no keep-self
  opt-out — and every active connection lease of the principal is revoked.
  The lease predicate is the principal, not the session digest, so leases
  minted before `portal_session_digest` existed are caught too. Every
  gateway replica's renew loop closes the bound streams within one renew
  cycle, and a replayed workspace-host cookie from any revoked session
  resolves to a dead lease (401) on any replica. Answers mirror logout:
  `204`, or `200 {"endSessionUrl"}` when the provider advertises
  `end_session_endpoint` and `oidc.endSession` is on — there is still no
  IdP back-channel logout. Unlike logout the revoke is atomic rather than
  best-effort: a store failure rolls the whole transaction back, the
  caller stays signed in and gets `500` — the operation is idempotent, so
  retrying is safe. One `session.revoke_all` audit event carries the
  per-kind counts; `tinycdi_session_revoke_all_total{result}` counts the
  calls. Migration 023 adds the two partial indexes backing the sweep —
  `connection_lease (tenant_id, principal_subject) WHERE state='active'`
  and `launch_ticket (tenant_id, principal_subject) WHERE consumed_at IS
  NULL AND revoked_at IS NULL` — expand-only, so replicas predating them
  simply seq-scan. The portal's account menu gains "Sign out everywhere"
  with a confirmation dialog (`en`/`vi`) that names the scope: all devices
  including this one, this tenant only.

**Per-user running-workspace limits** (#121)

- On top of the tenant quota — which stays tenant-scoped and unchanged —
  a tenant administrator can cap **concurrent running workspaces per
  principal**: a tenant-wide default plus optional per-user overrides, all
  API-managed (no config declaration, so writes are never refused as
  `QUOTA_MANAGED_BY_CONFIG`). New routes: `GET` and `PUT
  /v1/admin/tenants/{tenant}/user-limits` (per-principal override;
  `"limit": null` clears) and `PUT
  /v1/admin/tenants/{tenant}/user-limits/default` (the tenant fallback;
  `null` restores unlimited). The view reports the tenant `default`
  (`null` = unlimited) and one row per principal who has usage or a
  stored override — stored `limit`, resolved `effective`, current
  `running` — ordered by owner reference. Resolution order is **override →
  tenant default → unlimited**, and an upgrade carries no rows at all:
  **the default is unlimited, so nothing changes until an administrator
  sets a value** (migration 022 adds `tenant_user_limit_default` and
  `user_session_limit`, expand-only). Enforcement runs inside the same
  transaction — and the same `tenant_quota` row lock — as the quota
  reservation, so concurrent launches by one user can never overshoot;
  the count is derived live from held reservations, so a stopped Retain
  workspace's disk-only hold and retained data disks never count. A
  refusal is `409 QUOTA_EXHAUSTED` with `details.reason:
  UserLimitReached` and `details.params` `{limit, current}` — and
  `retryable: true` + `Retry-After` when the caller's own
  teardown-pending holds cover the shortfall. `GET /v1/quota` reports the
  caller's effective limit in `userLimits` and each user's in
  `users[].limit` (omitted when unlimited). Setting a limit below current
  usage is accepted: running workspaces keep running, new launches are
  refused. The admin portal gains a per-user limits section on the quota
  page and localized refusal copy; every request — reads and denied
  attempts included — emits an `admin.user_limit.*` audit event.

**Audit event coverage** (#120)

- Every mutating app route and every `/v1/admin/` route now emits exactly
  one dedicated audit event through the existing `AuditSink` — a
  request-scoped `audited()` wrapper records the verified pseudonymous
  actor, the target id, the tenant, the request id, the outcome
  (`success`/`failure`/`denied`) and the stable error code, and emits the
  event after the handler returns — so admin operations are
  reconstructable from the audit stream alone. New actions:
  `session.logout`, `workspace.create`/`.start`/`.stop`/`.delete`,
  `connection.create`, `data.attach`, `data.purge`, `admin.quota.get`/
  `.set` (#117 adds `session.revoke_all`, #121 `admin.user_limit.*`). A
  handler panic still emits its record (`failure`/`"panic"`). The
  config-driven tenant-quota apply writes `admin.quota.config_apply`
  (actor `config:tenant-quotas`, `requestId: "startup"`) — failed passes
  audited too, since a persistently failing apply must be visible.
  Gateway control endpoints audit denied bearer attempts under the
  operation they tried (`session.list`, `session.revoke`). Attempts
  refused before authentication stay covered by the per-request
  `http.request` record as before. `GuardedSink` wraps the sink so a write
  failure can never break a request: failures are counted on
  `tinycdi_audit_write_errors_total{event}` and logged once a minute with
  the suppressed count — alert on it, a nonzero rate means audit records
  are being lost. `docs/runbooks/observability.md` gains an audit
  section: the emitted actions and fields, what TinyCDI guarantees
  (emission and shape, redaction in the sink) vs what the operator must
  provide (collection, integrity, clock sync, Kubernetes audit logging).

**Intent-drift visibility** (#125)

- The applied-intent fence (`docs/runbooks/disaster-recovery.md`,
  "Workspace reconciliation") still never applies a stale intent — but a
  drop is no longer silent. When the applier drops an intent whose
  revision trails the CR's (or an equal revision describing different
  intent fields) — the signature of a platform database restored behind
  the live cluster — it stamps the
  `workspaces.cdi.tinyorbit.vn/intent-behind` annotation with the dropped
  and applied revisions. The operator reports a dedicated `IntentBehind`
  condition (`True`/`IntentBehind` with params `crRevision`/`rowRevision`,
  back to `False`/`Nominal` once the stream is realigned, absent entirely
  on a workspace that never drifted) and emits one edge-triggered
  `IntentBehind` Warning event on the transition into drift — the reason
  the operator ClusterRole gains `events` `create`/`patch`. The API
  surfaces the condition in the workspace status view and as a Warning
  lifecycle event; the portal renders it localized.

**Docs and hardening**

- Disaster-recovery runbook (#122): failure tiers and their recovery
  costs, measured RPO/RTO for the reference drill, the off-cluster backup
  set, copy-based PVC backup for clusters without a
  `VolumeSnapshotClass`, the full-cluster-loss procedure, and the new
  "Postgres-only restore onto a live cluster" section — see Operations.
  `hack/quickstart/restore-drill.sh` is the dev-only kind drill that
  exercises it end to end.
- Deploy-time chart guards (#119): `helm template`/`install` now fails
  on `operator.leaderElect: false` with `operator.replicas > 1` —
  unelected replicas would double-drive reconciliation (the binary
  cannot see the replica count, so the guard lives in `tinycdi.validate`;
  `replicas: 1` without election stays legal). The observability runbook
  now states the metrics-listener isolation rule — the unauthenticated
  `backend-metrics` ClusterIP Service must stay off the edge path — and
  chart tests pin that no `edgeIngress` mode ever opens the metrics port.
- Threat-model and test-inventory refresh (#128): the S14 row now
  records the v0.4 rate-limit details (breaker, restored budget
  defaults), S17/S18/S19 carry their v0.5 state, and new rows cover the
  v0.5 surface — S20 per-principal limits, S21 audit coverage, S22
  deploy guards, S23 live-cluster restore, S24 intent drift. ADR 0007 is
  marked Accepted with the as-merged implementation notes.
- CI flake fix (#127): the drain-window integration test issues probes
  only while provably inside the window — a test-side boundary race,
  not a product bug.

## Security

- **S17 defence-in-depth** (#123): every lease read that feeds renew,
  attach, claim, resolve or a foreign probe (`liveLease`) now
  re-validates the lease's bound portal session in the same indexed row
  read — the sessions row must exist and pass the current `session_epoch`
  and absolute-expiry check, the same semantics ticket redemption
  re-checks. A lease whose bound session is gone or invalid is revoked on
  the spot — before the gateway-identity check, so any caller kills the
  dead row — counted on
  `tinycdi_lease_session_missing_total{reason=absent|invalid}` and logged
  once. A lease resurrected `active` by a Postgres restore therefore dies
  at its next renew or attach even when the sign-out revoke itself was
  lost in the dump window, and a copied session cookie can never
  rehydrate it. Leases with a NULL `portal_session_digest` are exempt by
  design (rows minted before the binding column existed — revoking them
  on sight would mass-kill sessions mid-rolling-upgrade); they keep the
  TTL lifecycle and are covered by the post-restore lease sweep.
- **S18 closed** (#118, ADR 0008 — "accepted, no build required"): the
  open half of the KasmVNC brute-force question resolves as unreachable
  by construction. The pod endpoint sits behind a default-deny
  NetworkPolicy admitting only `role=gateway` pods; the gateway's
  cleaned-path allowlist forwards only stock client assets and
  `/websockify`; every proxied request needs a live session-bound lease;
  and `Authorization` is broker-injected on every proxied request, so no
  client class can present even one credential guess. The pod-side
  blacklist stays as correctly-keyed defence-in-depth.
- **Threat model refresh**: S19 (sign-out-everywhere vs the principal's
  other sessions) is recorded Implemented — tenant-scoped by design,
  atomic, no IdP back-channel — and S17's row now cites the lease/session
  check. The two open findings "metrics listener unauthenticated" and
  "operator leader election off by default" are resolved by #119's
  render-time guards and documentation. ADR 0007 (sign-out everywhere)
  and ADR 0008 (KasmVNC posture) land under `docs/adr/`; the security
  test inventory gained the new coverage entries.
- Measured on the v0.5.0-rc.1 e2e install (two replicas, upgraded from
  v0.4.0 with a live session): sign-out closed the live desktop stream
  within one 10 s renew cycle and a forced renew or attach answered 401
  on both replicas; sign-out everywhere closed the principal's sessions
  with streams on both replicas within one cycle; and a launch past a
  per-user limit answered `409 QUOTA_EXHAUSTED` with
  `details.reason: UserLimitReached` and the `limit`/`current` params.
- `POST /v1/me/sessions:revoke-all` is deliberately tenant-scoped and
  self-scoped: it needs only the caller's session + CSRF token, cannot
  reach other tenants' sessions, and is idempotent — a replay or race
  revokes zero rows.

## Operations

- **Never restore a Postgres dump onto a live cluster by hand.** The
  fencing that makes restored tickets and leases harmless on a rebuild
  (dead `runtimeUID`s, a foreign gateway) does not hold when the cluster
  kept running: restored `sessions` rows are indistinguishable from live
  ones (including sessions signed out after the dump), restored `active`
  leases rehydrate under their live digest bindings, unconsumed tickets
  re-arm, and `workspaces` rows diverge from the live CRs. The verified
  drill showed a signed-out cookie answering `200` again after a naive
  restore. `docs/runbooks/disaster-recovery.md` §"Postgres-only restore
  onto a live cluster" is the contract: freeze the platform (scale
  `backend` and `operator` to 0), load the dump, run the post-restore
  tool, scale back, reconcile workspaces vs live CRs in both directions
  (orphans/ghosts/diverged intent revisions — `IntentBehind=True` lists
  what still trails), rebuild retained inventory, settle quota drift.
- **`backend post-restore`** (#124) is the one-shot subcommand that runs
  the kill-steps deterministically: `session_epoch` rotation (every
  restored session row fails its next read), revoke every `active`
  `connection_lease`, deny every unconsumed `launch_ticket`, and align
  each `workspaces` row that trails its live CR
  (`desired_state`/`runtime_generation`/`intent_revision` from the CR's
  `spec`). Alignment is **forward-only**: a row's `intent_revision` moves
  up to the live CR's, never down — rewinding would re-present revisions
  the fence already recorded and break the gapless outbox stream. **The
  default is a dry-run** — plan plus affected row counts
  and the same two freeze probes, no writes, no lock taken. `-apply`
  requires `-i-have-scaled-down` (the operator's statement that the
  platform is frozen), then takes the leader advisory lock on a dedicated
  connection for the whole run — a held lock means a serving replica or a
  second run refuses with zero writes — and additionally refuses while
  `pg_stat_activity` still shows `tcdi-backend%` connections.
  `-i-know-backends-are-running` is the **UNSUPPORTED, dangerous**
  override for that second refusal only — serving replicas can create
  sessions and renew leases mid-apply. Other flags: `-database-url`
  (`TCDI_DATABASE_URL`), `-kubeconfig` (`KUBECONFIG`; default in-cluster),
  `-tenant-namespaces` (`TCDI_TENANT_NAMESPACES`; empty lists
  cluster-wide), `-dev-insecure-db` (dev only). Exit codes: `0` done/plan
  printed, `1` refused or failed, `2` usage/config, `3` Kubernetes read
  unavailable — without Kubernetes access the DB steps still run and the
  tool prints the per-workspace `UPDATE` plus the `kubectl jsonpath`
  that fills each value, exiting nonzero so the incomplete run is not
  silently green. Run it as a Job reusing the `backend` ServiceAccount
  and pod labels (the DB steps need no ServiceAccount token at all); the
  runbook carries the manifest. Idempotent; logs one summary line per
  run.
- **Audit shipping**: the audit stream is stdout JSONL — ship backend and
  gateway container logs to your log backend and alert on
  `tinycdi_audit_write_errors_total` and on
  `tinycdi_lease_session_missing_total` (a nonzero rate is either a
  restore resurrection or session-loss drift worth explaining).
- `hack/quickstart/restore-drill.sh` (dev only) exercises the live-cluster
  restore drill end to end on the kind quickstart, including the unsafe
  naive restore for contrast.

## Upgrading from v0.4.x

The procedure is `docs/runbooks/upgrade.md`; this upgrade carries schema
migrations, so read it and the points below before running it.

- **Back up the database first** (`pg_dump` per
  `docs/runbooks/backup-restore.md`). Migrations 022 and 023 are
  forward-only — there is no down migration, and `helm rollback` does not
  undo them: a real rollback is restoring the pre-upgrade dump.
- **Upgrade from v0.4.x.** Both new migrations are expand-only — 022 adds
  two tables (`tenant_user_limit_default`, `user_session_limit`), 023 two
  partial indexes — so a still-running v0.4.x replica never reads or
  writes them and the rolling window is safe; nothing contracts, so on
  contents alone they would not hard-fail an older replica either. The
  verified predecessor is nevertheless one minor back: a direct
  v0.3.x → v0.5 jump crosses the v0.4 hop's own gate (the
  `sessions.csrf_token` drop and the ADR-0006 semantics change) in the
  same window, a combination never exercised — step through v0.4.x first.
  v0.2.x is excluded outright for the reason the v0.4 notes give: a
  still-running v0.2 replica names `sessions.csrf_token` and fails the
  moment migration 019 drops it.
- **New metrics**: `tinycdi_session_revoke_all_total{result}` (#117),
  `tinycdi_lease_session_missing_total{reason}` (#123),
  `tinycdi_audit_write_errors_total{event}` (#120) — alert on the last
  two being nonzero.
- **New audit events**: `session.logout`, `session.revoke_all`,
  `workspace.create`/`.start`/`.stop`/`.delete`, `connection.create`,
  `data.attach`, `data.purge`, `admin.quota.get`/`.set`,
  `admin.quota.config_apply`, `admin.user_limit.*`, and denied-attempt
  records on the gateway control endpoints (`session.list`,
  `session.revoke`). If your log pipeline filters on `action`, widen it.
- **RBAC**: the operator ClusterRole gains `events` `create`/`patch` for
  the `IntentBehind` Warning event — the chart's `rbac.yaml` carries it
  for Helm installs; kustomize/`config` installs should re-apply
  `config/rbac/role.yaml`. The condition is still recorded without the
  grant, only the event emission fails.
- **No CRD change**: `IntentBehind` is a status condition on the existing
  Workspace kind (plus two metadata annotations); neither CRD schema
  changed.
- **Additive API surface** — no client action needed:
  `POST /v1/me/sessions:revoke-all`, the three
  `/v1/admin/tenants/{tenant}/user-limits` routes, `userLimits` +
  `users[].limit` on `GET /v1/quota`, `details.params` on errors, and the
  `IntentBehind` value in the condition-type enum. Older clients ignore
  all of it.
- **Chart**: no new required values, but the render now refuses the
  previously-accepted combination `operator.leaderElect: false` +
  `operator.replicas > 1` — a misconfiguration, not a regression; set
  `replicas: 1` or re-enable election.
- **Behaviour notes for mixed rollouts**: per-user limits are enforced
  only once every replica runs v0.5 (a v0.4 replica admits without the
  check); the lease/session check likewise runs only on v0.5 replicas, so
  a session revoked mid-rollout may linger until the last v0.4 replica
  stops serving renews — both settle with the rollout. Leases minted
  before `portal_session_digest` existed are exempt from the check by
  design.

- Measured on the v0.5.0-rc.1 e2e install: the v0.4.0 → v0.5.0-rc.1
  rolling upgrade dropped the live session ~1 s and resumed in-frame
  (same lease, no re-login), and migrations 022/023 applied cleanly. On
  a restored copy of a real deployment's database the migrations ran and
  `backend post-restore` verified both modes — a dry-run reporting the
  plan with zero writes, and `-apply` rotating `session_epoch`, revoking
  the restored leases, denying the outstanding tickets and aligning the
  diverged workspace rows forward. Soak on the same install (30 sessions
  with a full backend rollout mid-run): reconnect p95 1.95 s / p100
  3.0 s, input resume p100 12.3 s, 0 dropped sessions, 0 false lease
  revocations — PASS.

## Known limitations

- Not independently security-reviewed; a full review is planned before
  v1.0. The review-prep material — threat model (S18 closed, S17/S19
  Implemented, the v0.5 items S20–S24 recorded) and security test
  inventory — lives in `docs/security/`.
- "Sign out everywhere" is **tenant-scoped**: it ends every session the
  principal holds in the caller's tenant — sessions under other tenants
  are untouched — and there is no IdP back-channel logout; the provider
  session ends only via the same RP-initiated `endSessionUrl` navigation
  plain logout returns for the calling browser.
- Per-user limits cap **concurrent running workspaces only** — a stopped
  Retain workspace's disk-only hold, retained data disks and released
  reservations never count — and are tenant-admin managed per tenant;
  there is no platform-wide or config-declared per-user limit, and quota
  accounting stays tenant-scoped.
- The audit stream is stdout JSONL: TinyCDI guarantees emission and shape
  (verified actor, redaction, exactly one record per audited action) but
  not delivery or tamper evidence — collection, retention, integrity and
  clock sync are the operator's pipeline, and platform-level actions that
  never pass through TinyCDI (`WorkspaceTemplate` writes, Helm values,
  namespace changes) are covered only by Kubernetes audit logging.
- `backend post-restore`'s workspaces-alignment step needs Kubernetes
  read access; without it the tool still rotates/revokes/denies but
  prints the per-row SQL and exits nonzero — the operator must apply the
  printed `UPDATE`s to finish the job.
- Sandboxed runtimes: gVisor verified on kind (desktop/terminal;
  Firefox ESR does not start under runsc — its WASM in-process
  sandbox's segue setup is unimplemented and the process aborts
  ~7–13 s in, while the desktop session itself stays healthy); Kata
  untested. `kubectl port-forward` to a runsc pod does not work —
  gVisor sockets live in netstack, not the kernel netns — so use the
  Service/pod-IP path, as the gateway does. The full matrix and the
  weekly CI re-proof are in `docs/compatibility.md`.
- Server-originated free text is English only: the portal renders known
  event/condition `reason` templates — with their `params` — from the
  `en`/`vi` catalogs (#90, #111, #121, #125), but unknown tokens and
  other server messages still arrive in English.
